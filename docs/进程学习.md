# RespOS 线程学习笔记：从入门到精通

> 学习者定位：几乎没有内核基础。
>
> 学习方法：一次只理解一条主线，先建立直觉，再看 RespOS 代码。
>
> 代码基线：本文依据 2026-08-07 当前工作树整理；以当前源码为最终依据。

## 学习路线

我们不会在第一课就研究汇编和锁。计划按以下顺序慢慢学：

1. 线程是什么，为什么需要线程，线程怎样产生。
2. 线程如何获得 CPU：`Ready`、`Running` 与就绪队列。
3. 线程如何暂停和恢复：上下文、内核栈与 `__switch`。
4. 线程如何等待：`Blocked`、唤醒、sleep 与 futex。
5. 多个线程如何合作：共享内存、竞争、原子操作与锁。
6. 线程怎样结束：exit、`CHILD_CLEARTID`、futex 与 join。
7. 信号（上）：数据结构、发送路由、掩码。
8. 信号（下）：处理流程、sigreturn、与阻塞的配合。
9. 调度策略、TLS 与多核全景串联。

## 第 1 课：线程从哪里来？

### 1. 先不看内核：线程是什么？

把一个正在运行的程序想象成一家餐厅：

- **进程**像整家餐厅：它拥有店面、原料、菜单和收银台。
- **线程**像餐厅里的员工：每个人都有自己正在做到哪一步的记忆，却共享餐厅的场地和物资。
- **CPU**像真正能让员工干活的工作台。工作台少于员工时，大家需要轮流使用。
- **调度器**像领班：它决定下一个让谁使用工作台。

一句话定义：

> 线程是内核可以单独安排到 CPU 上运行的一条执行流。

“执行流”可以先粗略理解为：它知道自己下一条要执行哪条指令，也有自己的栈，因此能记住函数调用做到了哪里。

### 2. 线程有什么用？

一个程序只有一个线程时，一次只能沿一条路往下做。多个线程的主要作用是：

- **利用等待时间**：线程 A 等磁盘或网络时，线程 B 可以继续计算。
- **同时处理多件事**：例如一个线程处理界面，另一个线程下载数据。
- **利用多核 CPU**：在内核支持正确的前提下，多个线程可以真正同时运行。
- **低成本合作**：同一进程内的线程共享许多资源，交换数据比完全独立的进程更直接。

但“共享”也是危险的来源：两个线程同时修改一个数据，就可能互相破坏结果。这会是后面“同步”课程的主角，现在先留一个印象。

### 3. 进程和线程到底有什么不同？

先记住这张简化表：

| 东西 | 同一进程内的线程之间 |
| --- | --- |
| 程序代码 | 通常共享 |
| 用户内存/地址空间 | 共享 |
| 文件描述符表 | RespOS 的同组线程共享 |
| 线程号 `tid` | 每个线程独立 |
| 用户栈 | 每个线程独立 |
| 内核栈 | 每个线程独立 |
| 寄存器执行现场 | 每个线程独立 |

因此，“线程就是轻量进程”只能当入门比喻。更准确的说法是：

> 每个线程有自己的执行现场，同一进程的线程又共享一组进程资源。

### 4. RespOS 眼中的线程：Task

RespOS 内核常用 **task（任务）** 这个词。这是因为调度器最关心的不是人类如何称呼它，而是：“这是不是一个可以独立调度的对象？”

RespOS 中，每个可调度线程都有一个 `TaskControlBlock`，简称 **TCB**。可以把 TCB 想象成线程的“员工档案”。

TCB 定义在 `os/src/task/task.rs` 的 `TaskControlBlock` 中。它有很多字段，第一课只需要认识以下几个：

| 字段 | 现在怎样理解 |
| --- | --- |
| `tid` | 线程自己的唯一编号，像工号 |
| `tgid` | 线程组编号；同一进程的线程共用它 |
| `thread_group` | 记录同一线程组里有哪些线程 |
| `task_status` | 当前是就绪、正在运行、阻塞还是已退出 |
| `kernel_stack` | 这个线程进入内核后使用的独立栈 |
| `memory_set` | 用户地址空间；同进程线程会共享它 |
| `fd_table` | 文件描述符表；RespOS 的同组线程共享它 |

一个容易犯的错误是：把 TCB 当成线程本身。TCB 只是内核用来描述和管理线程的数据结构；线程真正运行时，是 CPU 按它保存的现场去执行指令。

### 5. 用户程序怎样提出“创建线程”请求？

常见的 C 程序会调用 `pthread_create(...)`。`pthread_create` 是用户态线程库提供的好用接口；内核底层看到的则是 `clone` 系统调用。

RespOS 的用户库封装在 `user/src/syscall.rs`：

```rust
pub fn sys_clone(flags: usize, stack: usize, ptid: usize, tls: usize, ctid: usize) -> isize
```

这里先只看两个参数：

- `flags`：一张“资源共享清单”，告诉内核新 task 要共享什么。
- `stack`：新线程自己的**用户栈**位置。

内核通过 `os/src/syscall/mod.rs` 把编号 220 分发给 `sys_clone`，实际处理函数在 `os/src/syscall/process.rs`。

### 6. `clone` 为什么需要 flags？

`clone` 不只是“再造一个 TCB”。它还要决定新 task 与旧 task 的关系。

第一课只记住三个标志：

| clone flag | 简单含义 |
| --- | --- |
| `CLONE_VM` | 共享用户地址空间 |
| `CLONE_SIGHAND` | 共享信号处理函数表 |
| `CLONE_THREAD` | 把新 task 加入同一线程组 |

RespOS 的 `sys_clone` 会检查：如果要求 `CLONE_THREAD`，就必须同时有 `CLONE_SIGHAND`；而 `CLONE_SIGHAND` 又必须配合 `CLONE_VM`。用白话说：

> 你既然说新 task 是同一进程的另一个线程，就不能又让它拥有一套完全独立的用户内存和信号处理表。

### 7. RespOS 创建线程的完整故事

现在把代码压缩成 8 步：

```text
用户线程调用 pthread_create / clone
        ↓
进入 RespOS sys_clone
        ↓
1. 检查 flags 是否合法
        ↓
2. 为新 task 分配 tid
        ↓
3. 为新 task 分配独立内核栈
        ↓
4. 复制当前线程的用户执行现场
        ↓
5. 按 flags 共享地址空间等资源，建立新 TCB
        ↓
6. 放入 thread_group 和 TASK_MANAGER
        ↓
7. 设置新线程的用户栈、TLS 和 clone 返回值
        ↓
8. add_task：放入调度器的就绪队列
```

下面把每步与当前 RespOS 源码对上。

#### 第 1 步：检查创建请求

`os/src/syscall/process.rs::sys_clone()` 把整数解释为 `CloneFlags`，并检查线程所需的共享关系是否合法。

#### 第 2～6 步：造出新 task

`sys_clone()` 调用：

```rust
let new_task = current_task.clone_(flags)?;
```

`os/src/task/task.rs::TaskControlBlock::clone_()` 做了几件关键的事：

1. `tid_alloc()` 分配新的线程号。
2. `KernelStack::new(&tid)` 分配独立内核栈。
3. `clone_trap_cx(...)` 复制调用者的用户寄存器现场。
4. 如果是 `CLONE_THREAD`，新 task 继承相同 `tgid`，并共享 `thread_group`。
5. 如果共享用户内存，直接共享同一个 `memory_set` 对象。
6. 建立新 `TaskControlBlock`，初始状态为 `Ready`。
7. 将它加入 `thread_group` 和全局 `TASK_MANAGER`。

`TASK_MANAGER` 可以先理解为按 tid 查找 task 的“花名册”。它不等于调度器的就绪队列。

#### 第 7 步：让父子看见不同的 clone 返回值

`sys_clone()` 会继续修改新 task 的 `TrapContext`：

- 把新线程的用户栈指针设为 `stack`。
- 需要时设置 TLS 指针；TLS 可以先理解为“每个线程自己的用户态小储物柜”。
- 把新 task 的 `a0` 设为 0。

于是同一次 `clone` 看起来像返回了两次：

| 谁继续运行 | 看到的返回值 |
| --- | --- |
| 创建者 | 新 task 的 tid |
| 新 task | 0 |

它并不是函数真的神奇执行了两次，而是内核造出了两份可以继续执行的现场，并故意在它们的返回值寄存器中填入不同值。

#### 第 8 步：新线程“出生了”，但还没开始跑

`sys_clone()` 最后调用：

```rust
add_task(new_task);
```

`os/src/task/scheduler.rs::add_task()` 把新 task 加入就绪队列。此时它的状态是 `Ready`，意思是：

> 我的身份、栈、资源和执行现场都准备好了，只等调度器给我 CPU。

稍后 `run_tasks()` 会通过 `fetch_task()` 选出它，把它从 `Ready` 变成 `Running`，再通过 `__switch` 切换过去。这是第 2、3 课的内容，本课先停在“进入就绪队列”。

### 8. 两种栈：第一课最容易混淆的地方

新线程至少需要分清两种栈：

| 栈 | 谁准备 | 用来做什么 |
| --- | --- | --- |
| 用户栈 | 通常由 pthread/用户线程库准备，通过 `clone` 的 `stack` 传入 | 执行用户函数，保存用户局部变量和函数调用 |
| 内核栈 | RespOS 在 `TaskControlBlock::clone_()` 中分配 | 线程进入内核处理系统调用、异常或中断时使用 |

为什么每个线程都要有自己的栈？因为栈记录了“我的函数执行到哪了”。如果两个线程共用同一个栈，它们会把对方的返回地址和局部变量相互覆盖。

### 9. 用 RespOS 现有测试代码印证这个模型

`user/src/bin/task_a_futex_exit_probe.rs` 里有一个直接创建线程的小例子。它的核心思路是：

1. 预留一块 `THREAD_STACK`。
2. 取这块空间的栈顶 `stack_top`。
3. 带着 `CLONE_VM | CLONE_SIGHAND | CLONE_THREAD` 调用 clone。
4. 创建者获得大于 0 的新 tid。
5. 新线程看见返回值 0，转去执行 `waiter_thread`。

这个 probe 后面还会涉及 futex 和线程退出，现在不需要读懂。它会在第 4～6 课重新出现。

### 10. 本课只需牢记的 6 句话

1. 线程是内核可以单独调度的一条执行流。
2. 同一进程的线程共享用户地址空间等资源，但有自己的 tid、栈和执行现场。
3. RespOS 用一个 `TaskControlBlock` 描述一个可调度 task。
4. 用户态的 `pthread_create` 底层会请求类似 `clone` 的内核能力。
5. `clone` 的 flags 决定新旧 task 共享哪些资源。
6. `add_task()` 只表示新线程已经 `Ready`；它什么时候真正运行，由调度器决定。

## 第 2 课：线程怎样真正获得 CPU？

### 1. 从第一课的结尾出发

第一课最后，新线程已经拥有 TCB、tid、用户栈、内核栈和执行现场，`sys_clone()` 调用了：

```rust
add_task(new_task);
```

但此时新线程只是 `Ready`，还不是 `Running`。

继续用餐厅的比喻：

- `Ready`：员工已经穿好工作服，正在候工区等待。
- `Running`：员工已经站到 CPU 工作台前，正在干活。
- 调度器：从候工区里选一个合适的员工。
- `Processor.current`：工作台边的牌子，写着“这个 CPU 当前正在运行谁”。

本课的主线只有这一条：

```text
Ready task
   ↓ add_task
进入就绪队列
   ↓ run_tasks
fetch_task 选中并认领
   ↓
Ready → Running
   ↓ Processor.current = next_task
__switch 把 CPU 交给它
```

### 2. 先认识线程的几种状态

RespOS 在 `os/src/task/task.rs` 中定义了 `TaskStatus`：

| 状态 | 大白话解释 |
| --- | --- |
| `Ready` | 什么都准备好了，正在等 CPU |
| `Running` | 已被某个 CPU 选中，正在或马上就要执行 |
| `Blocked` | 在等某件事，即使给它 CPU 也无法继续 |
| `Stopped` | 被停止信号暂停 |
| `Exited` | 已经结束 |

这一课只聚焦前两个：

```text
Ready --调度器选中--> Running
```

注意：`Ready` 不是“正在运行但比较慢”，而是“根本还没拿到 CPU”。

### 3. 三个容易混淆的地方

第一课已经接触了 `TASK_MANAGER`，现在又出现了就绪队列和 `Processor.current`。它们的用途完全不同：

| 结构 | 比喻 | 作用 |
| --- | --- | --- |
| `TASK_MANAGER` | 全公司员工花名册 | 通过 tid 查找一个 task |
| scheduler 就绪队列 | 候工队列 | 保存能运行、但正在等 CPU 的 task |
| `Processor.current` | CPU 工作台上的姓名牌 | 记录该 CPU 当前运行的 task |

一个 `Running` task 不应该还留在就绪队列里。否则另一个 CPU 可能再把它取走，导致同一线程被两个 CPU 同时执行。

### 4. 第一站：`add_task()` 把 task 放入哪里？

`os/src/task/scheduler.rs::add_task()` 主要做两件事：

```rust
assert!(task.is_ready());
SCHEDULER.lock().add(task);
```

第一句要求这个 task 必须已经是 `Ready`。不能把正在运行、已经阻塞或已退出的 task 随便塞进就绪队列。

第二句进入 `Scheduler::add()`，它会根据 task 的调度策略和优先级，将 task 放进合适的队列。

### 5. RespOS 不是只有一条就绪队列

当前 `Scheduler` 大致有三类队列：

| 队列 | 谁在里面 | 选择顺序 |
| --- | --- | --- |
| `rt_queues` | 实时调度 task | 数值更大的实时优先级更先 |
| `normal_queues` | 普通 task | nice 值更小的更先 |
| `idle_queue` | `SCHED_IDLE` task | 没有前两类可运行 task 时才考虑 |

同一档中，新进来的 task 通常放在队尾，选择时从前面取。可以先想成同一优先级下排队轮流。

本课不需要背调度策略的数值。现在只需要知道：

> 调度器不一定选最早来的 task，它先考虑调度类别和优先级。

### 6. 谁在不断挑选 task？`run_tasks()`

`os/src/main.rs` 在初始化完成后调用 `task::run_tasks()`。这是 RespOS 的调度循环入口。

`run_tasks()` 位于 `os/src/task/processor.rs`，可以先把它缩成：

```rust
loop {
    let next_task = fetch_task();
    if let Some(next_task) = next_task {
        // 记录这个 CPU 即将运行它
        processor.switch_to(next_task);
        // 真正切换执行现场
        __switch(...);
    }
}
```

真实代码还要处理多核、idle 和安全交接，所以更长。但它的骨架就是：

1. 找下一个 task。
2. 找到就记录为当前 task。
3. 切换过去。
4. 如果找不到，CPU 进入 idle，等待中断或新工作。

### 7. `fetch_task()` 不只是“从队头拿一个”

`os/src/task/scheduler.rs::fetch_task()` 是这一课的核心。它大致做三步：

#### 第一步：确定当前 CPU

多核系统中，调度器必须知道“是哪个 CPU 在要工作”。不同 task 可能设置了 CPU affinity，也就是只允许在某些 CPU 上运行。

#### 第二步：`fetch_for_cpu(cpu)` 选择合适 task

它按大致的优先级顺序扫描就绪队列，并跳过不允许在该 CPU 上运行的 task。被跳过的 task 仍留在队列中，等它允许的 CPU 来取。

#### 第三步：认领 task

选中后，`try_claim_running_on_cpu(cpu)` 会：

1. 再次确认状态是 `Ready`。
2. 确认没有其他 CPU 拥有它的执行现场。
3. 把当前 CPU 记为这个 task 的 owner。
4. 把状态改为 `Running`。

可以把 claim 想象成从候工员工手里取走排队号，然后给他盖上“已由 CPU 2 接走”的章。其他 CPU 再来时，就不能重复接走他。

### 8. 为什么先改成 `Running`，后调用 `__switch`？

你可能会问：此时 CPU 还没真正执行新 task，为什么先把它标成 `Running`？

因为这里的 `Running` 更准确地表示：

> 这个 task 已被某个 CPU 独占认领，别的 CPU 不得再选它。

如果先从队列中取出 task，但很晚才改状态，其他唤醒路径或 CPU 可能在中间窗口对它作出错误判断。

当前 RespOS 把“从队列选出”和“改成 `Running`”放在同一把 scheduler 锁的保护期间内，又用 CPU owner 防止执行现场被重复恢复。这是多核下的正确性保护。

第二课不要尝试理解原子操作的每个细节，先记住目标：

> 一个 task 在任何时刻最多只能被一个 CPU 当作 `Running`。

### 9. `Processor.current` 的作用

task 被 `fetch_task()` 认领后，`run_tasks()` 调用：

```rust
processor.switch_to(next_task.clone());
```

`switch_to()` 的核心就是：

```rust
self.current = Some(task);
```

这表示当前 CPU 从此可以回答：“我现在正在运行哪个 task？”

很多内核操作都需要这个答案。例如线程调用 `getpid` 或访问自己的地址空间时，内核先要知道当前 task 是谁。

### 10. 最后一步：`__switch`

到目前为止，内核只是：

- 选好了 next task。
- 把它认领为 `Running`。
- 在 `Processor.current` 中记录了它。

真正让 CPU 从调度循环转去执行新 task，需要：

```rust
__switch(next_task_kstack, idle_task_ptr);
```

`__switch` 会换上新 task 保存的执行现场。对第一次运行的新线程来说，这份现场最终会引导 CPU 返回用户态，从 clone 返回值为 0 的分支继续。

这里只需要把 `__switch` 当作一扇门：

```text
门这边：idle 调度上下文
       ↓ __switch
门那边：next task 的执行上下文
```

下一课才会打开这扇门，看清“执行现场”到底是什么。

### 11. 一个完整小例子

假设就绪队列中有普通 task A 和 task B，CPU 0 当前没有用户 task 可运行：

```text
就绪队列：[A, B]
CPU 0 current：None
```

CPU 0 的 `run_tasks()` 开始工作：

1. `fetch_task()` 调用 `fetch_for_cpu(0)`。
2. A 允许在 CPU 0 运行，因此 A 被从队列取出。
3. A 被 CPU 0 claim，状态从 `Ready` 变为 `Running`。
4. `Processor.current` 记录 A。
5. `__switch` 恢复 A 的执行现场，A 开始执行。

结果：

```text
就绪队列：[B]
CPU 0 current：A
A.status：Running
B.status：Ready
```

如果 A 只允许在 CPU 1 运行，CPU 0 会跳过 A，尝试选择可以在 CPU 0 上运行的 B；A 仍保留在就绪队列里。

### 12. 本课最容易误解的 5 件事

1. **`Ready` 不是 `Running`**：前者在等 CPU，后者已被 CPU 认领。
2. **花名册不是就绪队列**：`TASK_MANAGER` 用来查找，scheduler 队列用来排队。
3. **选中 task 不等于已完成硬件切换**：`fetch_task()` 负责选择和认领，`__switch` 才负责换执行现场。
4. **调度不是永远简单先来先服务**：还要看调度类别、优先级和 CPU affinity。
5. **同一 task 不能被两个 CPU 同时认领**：所以需要 scheduler 锁和 CPU owner。

### 13. 本课只需牢记的 6 句话

1. `Ready` 表示等 CPU，`Running` 表示已被某个 CPU 认领。
2. `add_task()` 把 `Ready` task 放入调度器的合适就绪队列。
3. `run_tasks()` 是不断寻找下一个 task 的调度循环。
4. `fetch_task()` 选择当前 CPU 可以运行的 task，并将它 claim 为 `Running`。
5. `Processor.current` 记录当前 CPU 正在运行谁。
6. `__switch` 才负责换上新 task 的真正执行现场。

2. `TASK_MANAGER`、就绪队列和 `Processor.current` 分别做什么？
3. `add_task()` 为什么先断言 task 必须是 `Ready`？
4. `fetch_for_cpu(cpu)` 为什么可能跳过队列中的某个 task？
5. task 被 `fetch_task()` 选中后，为什么不立即让其他 CPU 再选它？
6. `fetch_task()` 和 `__switch` 的分工是什么？

<details>
<summary>参考答案</summary>

1. `Ready` 已经具备运行条件，但正在等 CPU；`Running` 已被某个 CPU 独占认领。
2. `TASK_MANAGER` 用 tid 查找 task；就绪队列存放等待 CPU 的 task；`Processor.current` 记录某 CPU 当前运行的 task。
3. 只有已经具备运行条件的 task 才能进入就绪队列，否则队列与状态会自相矛盾。
4. task 可能因 CPU affinity 不允许在当前 CPU 运行，或者它的执行现场还归另一个 CPU 所有。
5. 否则同一线程的寄存器现场和内核栈可能被两个 CPU 同时使用，造成严重损坏。
6. `fetch_task()` 负责选择、移出队列和认领 task；`__switch` 负责真正保存/恢复执行现场，把 CPU 交给新 task。

## 第 3 课：CPU 怎样暂停和恢复线程？

### 1. 从一个困惑开始

第 2 课结束时我们停在了这里：

```text
run_tasks() → fetch_task() → 认领 next_task → __switch(...)
```

`__switch` 被描述为”一扇门”：门这边是 idle 调度上下文，门那边是 next task 的执行上下文。

本课要打开这扇门，回答一个核心问题：

> CPU 只有一套寄存器。线程 A 正在用它们计算，线程 B 也需要用它们计算。CPU 怎样做到”暂停 A、恢复 B”，让两者都感觉不到对方的存在？

答案是**上下文切换**。在动手看 `__switch` 的汇编之前，先建立直觉。

### 2. 什么是”上下文”？

把 CPU 想象成一个正在做复杂手工的工匠。他手边有：

- **双手正在做的东西**：当前指令操作的数据（通用寄存器）
- **图纸上指到哪一步了**：下一条指令的地址（`sepc` / 程序计数器）
- **工作台的状态**：权限模式、中断开关等（`sstatus` 等 CSR）
- **当前用哪张图纸**：页表（`satp`）
- **工具箱里的备用材料**：调用者保存的临时寄存器
- **私人储物柜里的东西**：被调用者保存的寄存器（`s0-s11`）

当工匠需要暂停工作 A 去处理工作 B 时，他必须：

1. 把工作 A 的所有”做到一半的状态”记录下来。
2. 拿出工作 B 之前记录的状态，摆回工作台。
3. 从工作 B 上次中断的地方继续。

这份”做到一半的状态”就是**上下文（Context）**。

RespOS 中有两种上下文，它们的分工非常明确：

| 上下文 | 保存在哪 | 谁保存/恢复 | 什么时候用 |
| --- | --- | --- | --- |
| `TrapContext` | 内核栈顶部 | `__trap_from_user` / `__restore` | 用户态 ↔ 内核态切换 |
| `TaskContext` | 内核栈上（在 TrapContext 下方） | `__switch` | 内核态线程 A → 线程 B 切换 |

用一句话记住它们的区别：

> `TrapContext` 记录”用户程序执行到哪了”；`TaskContext` 记录”内核代码执行到哪了”。

### 3. 故事：线程 A 被时钟中断，切换到线程 B

这是理解上下文切换最完整的路径。我们从头到尾走一遍。

#### 第一阶段：线程 A 在用户态运行

线程 A 正在用户态执行它的代码。CPU 寄存器里全是 A 的数据，`sepc` 指向 A 的下一条用户指令，`sstatus` 的 SPP 位是 User。

#### 第二阶段：时钟中断发生

硬件定时器触发，CPU 强制跳转到 `stvec` 指向的 `__trap_from_user`。

`__trap_from_user` 做的事情（`os/src/arch/rv64/trap/trap.S:24-83`）：

```text
1. 通过 sscratch 切换到当前任务的内核栈
2. 在内核栈上分配 -68*8 字节的空间（就是 TrapContext 的大小）
3. 保存所有 32 个通用寄存器 (x0-x31)
4. 保存 sstatus、sepc
5. 保存所有 32 个浮点寄存器 + fcsr
6. 调用 trap_handler(cx)
```

此时内核栈的顶部是一个完整的 `TrapContext`，它冻结了线程 A 在用户态的**全部**寄存器状态。

`TrapContext` 定义在 `os/src/arch/rv64/trap/context.rs`：

```rust
pub struct TrapContext {
    pub x: [usize; 32],        // 通用寄存器 x0-x31
    pub sstatus: Sstatus,      // 特权状态（返回哪个特权级等）
    pub sepc: usize,           // 异常返回后执行哪条指令
    pub f: [usize; 32],        // 浮点寄存器 f0-f31
    pub fcsr: usize,           // 浮点控制状态寄存器
}
```

注意：`TrapContext` 记录的是**用户态**的寄存器。此时 CPU 已经在内核态执行 `trap_handler`，它使用的寄存器（`sp`、`ra`、`t0-t6` 等）是内核自己的，可以随意使用——用户的已经安全存好了。

#### 第三阶段：`trap_handler` 判断为时钟中断

`trap_handler`（`os/src/arch/rv64/trap/mod.rs:81`）读取 `scause`，发现是 `SupervisorTimer` 中断。它调用 `preempt_current_task()`。

#### 第四阶段：`preempt_current_task()` → `handoff_current_to_idle()` → `__switch`

`preempt_current_task()` 获取当前 task（线程 A），调用 `handoff_current_to_idle(task)`。

`handoff_current_to_idle` 在 `os/src/task/processor.rs:150-161`：

```rust
pub fn handoff_current_to_idle(current: Arc<TaskControlBlock>) {
    let idle_task = current_idle_task();
    let idle_kstack = idle_task.kstack();
    // 把 current 从 Processor 移入 handoff 槽
    processor.handoff_current(&current);
    // 关键：切换到 idle 上下文
    unsafe {
        __switch(idle_kstack, Arc::as_ptr(&current) as usize);
    }
}
```

现在终于轮到 `__switch` 了。它的两个参数是：
- `a0`：**下一个**任务的内核栈指针（idle task 的）
- `a1`：**当前**任务的 TCB 指针（线程 A 的）

### 4. `__switch` 逐行解读

`__switch` 在 `os/src/arch/rv64/task/switch.S`。我们按”保存当前 → 切换到下一个”两段来读。

#### 保存当前（线程 A）的上下文

```asm
__switch:
    # 在内核栈上留出 TaskContext 的空间（16 × 8 = 128 字节）
    addi sp, sp, -16*8

    # 保存 ra（返回地址）—— 这记录了内核代码执行到哪了
    sd ra, 0(sp)
    # 保存 tp（线程指针）—— 指向当前 CPU 的 PerCpu 结构
    sd tp, 8(sp)

    # 保存 s0-s11（被调用者保存寄存器）
    # 这些是 C 编译器保证在函数调用后不会变的寄存器
    sd s0,  2*8(sp)
    sd s1,  3*8(sp)
    ...
    sd s11, 13*8(sp)

    # 保存 satp（页表基址寄存器）
    csrr t0, satp
    sd t0, 14*8(sp)

    # 关键：把当前 sp 写回线程 A 的 TCB.kernel_stack.top
    # a1 = 线程 A 的 TCB 指针
    # TCB 第一个字段是 kernel_stack，kernel_stack 第一个字段是 top
    sd sp, 0(a1)
```

`TaskContext` 结构定义在 `os/src/task/context.rs`：

```rust
pub struct TaskContext {
    ra: usize,          // 返回地址（偏移 0）
    tp: usize,          // 线程指针（偏移 8）
    s: [usize; 12],     // s0-s11（偏移 16 ~ 111）
    mmu_token: usize,   // satp 值（偏移 112）
    _padding: usize,    // 对齐填充（偏移 120）
}
```

注意 `__switch` 保存的寄存器非常少——只有 `ra`、`tp`、`s0-s11` 和 `satp`。它**不需要**保存 `t0-t6`、`a0-a7` 等临时寄存器。

为什么？因为 `__switch` 是以**函数调用**的形式使用的。在 RISC-V 调用约定中：

- **调用者保存寄存器**（`t0-t6`、`a0-a7`、`ra`）：调用者已经预期函数可能修改它们，调用者自己会保存。
- **被调用者保存寄存器**（`s0-s11`、`sp`）：被调用函数必须保证返回时这些寄存器不变。

`__switch` 不返回（它返回到另一个上下文），但它必须保存 `s0-s11`——因为从下一个任务的视角看，它当初调用 `__switch` 时，编译器认为 `s0-s11` 在 `__switch` 返回后应该还是原来的值。

简单地说：`__switch` 保存的是”编译器认为函数调用不会破坏的寄存器”。

#### 恢复下一个（idle）的上下文

```asm
    # a0 = idle task 的内核栈指针（指向它之前保存的 TaskContext）

    # 恢复 ra —— 这决定了 “切换到 idle 后从哪里开始执行”
    ld ra, 0(a0)
    # 恢复 tp
    ld tp, 8(a0)

    # 恢复 s0-s11
    ld s0,  2*8(a0)
    ...
    ld s11, 13*8(a0)

    # 恢复 satp（切换页表！）
    ld t0, 14*8(a0)
    csrw satp, t0
    # 刷新 TLB（页表缓存），因为页表可能变了
    sfence.vma

    # 弹出 TaskContext，恢复内核栈指针
    addi a0, a0, 16*8
    mv sp, a0

    # 返回到 ra 指向的地址
    ret
```

`ret` 指令跳转到 `ra` 寄存器的值。对于 idle task，它的 `TaskContext.ra` 就是 `run_tasks()` 循环中 `__switch` 的下一行。所以 CPU 回到了 idle 循环。

#### 线程 A 现在是什么状态？

线程 A 的执行现场被冻结在两个地方：

```text
内核栈顶部：TrapContext（用户态寄存器，由 __trap_from_user 保存）
        ↓
   TaskContext（内核态寄存器，由 __switch 保存）
        ↓
   剩余内核栈空间（可用）
```

线程 A 的 `kernel_stack.top` 现在指向 `TaskContext` 的位置。下次有人要恢复线程 A 时，只需要把它的 `kstack()` 值传给 `__switch` 的 `a0`。

### 5. idle 循环做了什么？

CPU 回到 idle 上下文后，`run_tasks()` 的循环继续：

1. `publish_saved_handoff()`：idle 发现线程 A 已经被 handoff 过来。如果 A 仍然是 `Running` 且没有被终止，idle 把 A 标记回 `Ready`，重新放入就绪队列。
2. 清理死亡任务。
3. `fetch_task()` 选出下一个可运行的 task（比如线程 B）。
4. `processor.switch_to(B)`，记下”当前 CPU 运行 B”。
5. 再次调用 `__switch(B.kstack(), idle_task_ptr)`。

这次 `__switch`：
- 把 idle 的上下文保存到 idle task 的内核栈。
- 从 B 的内核栈恢复 B 的上下文。
- `ret` 到 B 的 `TaskContext.ra`。

### 6. 新线程第一次被 `__switch` 恢复时

线程 B 可能是刚通过 `clone` 创建的。回顾第 1 课，新线程的内核栈上预先写好了两个结构（从栈顶往下）：

```text
栈顶边界 ─── TrapContext（由 clone_trap_cx 复制自父线程）
        ─── TaskContext（由 write_task_cx 写入）
        ─── 可用栈空间...
```

`TaskContext` 是通过 `app_init_task_context(token)` 创建的：

```rust
pub fn app_init_task_context(token: usize) -> Self {
    Self {
        ra: __restore as *const () as usize,  // ← 关键！
        tp: 0,
        s: [0; 12],
        mmu_token: token,
        _padding: 0,
    }
}
```

注意 `ra` 被设为 `__restore` 的地址。所以 `__switch` 的 `ret` 不会回到某个”调用 `__switch` 的地方”——它直接跳到了 `__restore`！

### 7. `__restore`：从内核栈恢复到用户态

`__restore` 在 `os/src/arch/rv64/trap/trap.S:85-130`。它做的事情正好与 `__trap_from_user` 相反：

```text
1. 从内核栈上的 TrapContext 恢复 sstatus、sepc
2. 恢复所有 32 个浮点寄存器
3. 恢复通用寄存器 x1-x31（除了 x5/x6 最后恢复）
4. 恢复 sscratch
5. 设置 stvec 指向 __trap_from_user（为下次异常做准备）
6. 恢复用户栈指针 sp（指向用户栈！）
7. 设置 sstatus.SPP = User
8. sret（硬件自动切换到 U 模式，跳转到 sepc）
```

对新线程来说：
- `TrapContext.sepc` 指向用户程序的入口点（或 clone 返回后的下一条指令）
- `TrapContext.x[2]`（sp）指向它自己的用户栈
- `TrapContext.x[10]`（a0）被设为 0（clone 对子线程返回 0）

于是新线程在用户态”诞生”了，它看到 clone 返回了 0，继续执行用户代码。

### 8. 完整的生命周期图

把以上串起来，一个线程的完整执行路径：

```text
                    ┌── 线程第一次运行 ──┐
                    │                   │
              __switch ──→ __restore ──→ 用户态执行
                    │                   │
                    │              syscall / 中断 / 异常
                    │                   │
                    │           __trap_from_user
                    │                   │
                    │            trap_handler()
                    │                   │
                    │     ┌─────────────┴─────────────┐
                    │     │       调度决策：           │
                    │     │  yield / preempt / block   │
                    │     │  / exit / signal           │
                    │     └─────────────┬─────────────┘
                    │                   │
                    │     handoff_current_to_idle()
                    │                   │
                    └── __switch（回到 idle）──┘
                                        │
                                   run_tasks() 循环
                                        │
                                   fetch_task()
                                        │
                                   __switch（到下一个线程）
                                        │
                                   __restore → 用户态
```

关键洞察：**用户线程从不直接切换到另一个用户线程**。中间一定经过内核的 idle 上下文。路径是：

```text
用户 A →(异常)→ 内核 A →(__switch)→ idle →(__switch)→ 内核 B →(__restore)→ 用户 B
```

### 9. 内核栈：为什么每个线程一个？

现在可以更深刻地理解第 1 课的问题了。看图：

```text
线程 A 的内核栈                    线程 B 的内核栈
┌──────────────────┐              ┌──────────────────┐
│   TrapContext    │ ← 栈顶边界   │   TrapContext    │
│   (用户寄存器)    │              │   (用户寄存器)    │
├──────────────────┤              ├──────────────────┤
│   TaskContext    │ ← kstack()   │   TaskContext    │
│   (内核寄存器)    │              │   (内核寄存器)    │
├──────────────────┤              ├──────────────────┤
│                  │              │                  │
│   可用栈空间      │              │   可用栈空间      │
│   (函数调用等)    │              │   (函数调用等)    │
│                  │              │                  │
└──────────────────┘              └──────────────────┘
```

`__switch` 的核心操作就是：
1. 把当前 sp 存入”当前线程 TCB 的第一个字段”（`sd sp, 0(a1)`）。
2. 从”下一个线程的内核栈”加载新 sp 和新寄存器（从 `a0` 指向的位置读取）。

两个线程的内核栈互不干扰，各自保存着自己在内核中的”做到一半的状态”。

### 10. 为什么需要 idle task？

你可能想问：为什么切换必须经过 idle，不能从线程 A 的 `__switch` 直接到线程 B？

在多核系统中，这是一个安全约束。如果线程 A 还在执行 `__switch` 的后半段（比如正在恢复寄存器），另一个 CPU 可能已经把它从就绪队列取出并尝试再次恢复它。这会导致同一个线程的内核栈被两个 CPU 同时使用。

RespOS 的多核设计：线程 A 先切到 idle，idle 在 `publish_saved_handoff()` 中确认线程 A 已经完全离开 CPU 后，才把 A 放回全局就绪队列。这样就保证了每个线程的内核栈在任何时刻最多被一个 CPU 使用。

在第 2 课中我们学过 `cpu_owner` 字段和 `try_claim_running_on_cpu()`，现在可以看到完整的配合：状态标记（`Running` + `cpu_owner`）和实际的硬件切换（`__switch`）通过 idle 这个”安全交接区”协作。

### 11. 触发上下文切换的几种场景

RespOS 中，以下场景都会走到 `__switch`：

| 场景 | 入口函数 | 当前线程之后怎样 |
| --- | --- | --- |
| 时钟中断（时间片到了） | `preempt_current_task()` | 放回就绪队列队尾 |
| 主动让出 CPU | `yield_current_task()` | 放回就绪队列 |
| 等待 futex / 睡眠 | `blocking_and_run_next()` | 变为 Blocked，不放回队列 |
| 信号停止 | `stop_current_and_run_next()` | 变为 Stopped |
| 线程/进程退出 | `exit_and_run_next()` | 变为 Exited，资源回收 |
| idle 选下一个 | `run_tasks()` 循环 | idle 本身不进入就绪队列 |

它们都调用 `handoff_current_to_idle(task)` → `__switch(idle_kstack, task_ptr)`。区别只在于从 `__switch` 返回后，idle 如何处置被 handoff 的 task。

### 12. 两种上下文的分工再澄清

容易搞混的一个地方是：`trap_handler` 返回后去了哪里？

答案是 `__restore`（`trap.S:83` 的 `j __restore`）。正常处理完异常后，`__restore` 恢复同一个线程的 TrapContext，`sret` 回到用户态。这**不是**上下文切换——同一个线程只是暂时进入内核又退出。

真正的线程切换发生在：`trap_handler` → 调度函数 → `handoff_current_to_idle` → `__switch` → idle → `__switch` → 另一个线程的内核上下文 → `__restore` → 另一个线程的用户态。

### 13. 本课只需牢记的 7 句话

1. `TrapContext` 保存用户态的全部寄存器，位于内核栈顶部；由异常入口保存，`__restore` 恢复。
2. `TaskContext` 只保存内核态的”被调用者保存寄存器”（`ra`、`tp`、`s0-s11`、`satp`），由 `__switch` 保存和恢复。
3. `__switch` 的核心是：当前 sp → 写入 TCB，从下一个内核栈 → 加载新 sp 和新寄存器，然后 `ret`。
4. 新线程的 `TaskContext.ra` 被设为 `__restore`，所以它第一次被 `__switch` 选中时，`ret` 直接进入异常返回路径，回到用户态。
5. 线程切换从不直接从用户 A 到用户 B，必须经过 `内核 A → idle → 内核 B`。
6. 每个线程有独立的内核栈，这是上下文切换不互相破坏的基础。
7. Idle task 不只是”空转”，它是多核安全交接的关键——确保旧线程完全离开 CPU 后才被放回就绪队列。

### 14. 自测

1. `TrapContext` 和 `TaskContext` 保存的内容有什么不同？为什么需要两种？
2. `__switch` 为什么只保存 `ra`、`tp`、`s0-s11` 和 `satp`，不保存 `t0-t6`？
3. 新线程第一次被 `__switch` 恢复时，`ret` 会跳转到哪里？为什么？
4. 为什么线程 A 不能直接 `__switch` 到线程 B，必须经过 idle？
5. 线程 A 的”执行现场”被冻结在哪些数据结构里？下次恢复时从哪开始？
6. 时钟中断发生后，从 `__trap_from_user` 到线程 B 的用户代码，中间经过了哪些关键步骤？

<details>
<summary>参考答案</summary>

1. `TrapContext` 保存用户态的全部 32 个通用寄存器 + 浮点寄存器 + `sstatus`/`sepc`，因为返回用户态时需要完整恢复用户看到的一切。`TaskContext` 只保存内核态执行到一半时的被调用者保存寄存器，因为 `__switch` 以函数调用形式工作，调用者保存寄存器已经由编译器在调用处保存。
2. 因为 RISC-V 调用约定规定 `t0-t6` 是调用者保存寄存器——调用 `__switch` 的代码已经预期这些寄存器可能被修改。从”被切换的线程”的视角看，它调用 `__switch` 之后返回时，只需要保证 `s0-s11` 不变。
3. 跳转到 `__restore`。因为新线程的 `TaskContext` 由 `app_init_task_context` 创建，它把 `ra` 设为了 `__restore` 的地址。`__restore` 随后从内核栈恢复 `TrapContext`，`sret` 到用户态。
4. 多核安全：线程 A 在执行 `__switch` 后半段时内核栈仍在使用中。如果直接切到 B，A 的 CPU owner 尚未释放，但 A 可能已被放入就绪队列，另一个 CPU 可能取走 A 并再次恢复它的内核栈，导致两个 CPU 同时使用同一内核栈。idle 作为中间站，确认旧线程完全离开后才把它发布回就绪队列。
5. 冻结在两个地方：`TrapContext`（在内核栈顶部，保存进入内核时的用户态寄存器）和 `TaskContext`（在 TrapContext 下方，保存调用 `__switch` 时的内核态寄存器）。下次恢复时从 `kstack()` 指向的 `TaskContext` 开始，加载 `ra` → `ret` 回到内核代码（通常是 `__restore`），再 `sret` 回用户态。
6. 用户 A 代码 → 时钟中断硬件 → `__trap_from_user`（保存 TrapContext）→ `trap_handler`（识别为时钟中断）→ `preempt_current_task()` → `handoff_current_to_idle(A)` → `__switch`（保存 A 的 TaskContext，恢复 idle）→ idle `publish_saved_handoff`（将 A 放回就绪队列）→ `fetch_task`（选 B）→ `__switch`（保存 idle，恢复 B 的 TaskContext）→ `ret` 到 B 保存的 `ra`（可能是 `__restore`）→ `__restore`（恢复 B 的 TrapContext）→ `sret` → 用户 B 代码。

</details>

## 第 4 课：线程怎样等待和唤醒？

### 1. 场景

线程经常需要等——等锁、等 I/O、等时间。当前线程无法继续时，它要**暂停自己**，等条件满足后**被叫醒**。

### 2. 状态转换：加入 Blocked

```
        add_task()          fetch_task()
新建 ──────────→ Ready ──────────→ Running
                   ↑                   │
                   │                   │ 等某件事
                   │                   ↓
              wakeup_task           Blocked
                   ↑                   │
                   └───────────────────┘
```

| 状态 | 在就绪队列？ | fetch_task 能选？ | 怎么变回去 |
| --- | --- | --- | --- |
| Ready | ✓ | ✓ | — |
| Running | ✗ | 已被选中 | 换下 → Ready / Blocked |
| Blocked | ✗ | ✗ | `wakeup_task` → Ready |

### 3. block vs preempt

```
preempt: Running → handoff → idle放回就绪队列 → 早晚再跑（线程无感知）
block:   Running → set_blocked → 放入blocked_tasks → 切走（线程主动等，需要被叫醒）
```

阻塞的线程**不在就绪队列**，没人叫就永远不会跑。

### 4. 核心函数：`blocking_and_run_next`（scheduler.rs:222）

```rust
pub fn blocking_and_run_next() {
    let task = current_task();
    task.set_blocked();        // Running → Blocked
    block_task(task);          // 从就绪队列移除，放入 blocked_tasks
    switch_to_next_task();     // 切走，等被叫醒
}
```

`blocked_tasks` 是 `Scheduler` 里的 `HashMap<tid, TCB>`。线程阻塞后只存在于这里，别处找不到。

### 5. 核心函数：`wakeup_task`（scheduler.rs:587）

```rust
pub fn wakeup_task(tid: usize) {
    let task = scheduler.wake(tid);  // 从 blocked_tasks 取出
    task.set_ready();                 // Blocked → Ready
    scheduler.add(task);              // 放回就绪队列
    kick_one_idle_hart_in(affinity);  // 通知空闲 CPU
}
```

### 6. `switch_to_next_task`（scheduler.rs:166）

```rust
loop {
    if current.is_running() { return; }  // 被叫醒了，继续执行
    handoff_current_to_idle(current);    // 还是 Blocked，交出 CPU
}
```

醒来后 `is_running()` 为 true，循环退出，返回到 `blocking_and_run_next` 的调用者继续往下走。

### 7. 谁调用 wakeup_task？

线程自己已经阻塞，不能叫醒自己。必须外部触发：

| 触发源 | 场景 |
| --- | --- |
| 另一个线程调 `futex_wake` | 释放了锁 |
| 内核定时器 `check_futex_timeouts` | sleep 时间到了 |
| 信号送达 | SIGKILL 等 |

最终都走同一句 `wakeup_task(tid)`。

### 8. futex 机制

最基本的等待/唤醒原语：

```
futex_wait(&addr, val):   如果 *addr==val → 阻塞自己
futex_wake(&addr, n):    唤醒等 addr 的至多 n 个线程
```

futex 线程同时登记在两处：
- **FUTEX_QUEUES**（`futex/queue.rs`）：256 个哈希桶，记录”谁在等哪个地址”
- **blocked_tasks**：记录”谁是 Blocked 状态”

两处各司其职：futex_wake 按地址查 FUTEX_QUEUES 找到 tid，再调 `wakeup_task` 从 blocked_tasks 取出放入就绪队列。

### 9. 带超时的等待

`futex_wait` 可以带一个 timeout：

```
线程 A: futex_wait(&addr, expected_val, timeout=5s)
```

futex 模块会把 A 登记到 `FUTEX_WAITS` 结构里（`futex/wait.rs:58`），记录 deadline = 现在 + 5s。内核定时器定期调 `check_futex_timeouts()`（`futex/wait.rs:372`），扫描有无超时者：

```rust
pub fn check_futex_timeouts() {
    let expired = FUTEX_WAITS.lock().expire(get_time_us(), get_timeout_us());
    for tid in expired {
        wakeup_task(tid);   // 超时也走同一个唤醒路径
    }
}
```

A 醒来后 `futex_wait` 返回 `-ETIMEDOUT`。普通 `sleep(seconds)` 底层也是同样的定时阻塞机制。

### 10. 三种离开 CPU 的方式

| | preempt（抢占） | yield（主动让出） | block（阻塞等待） |
| --- | --- | --- | --- |
| 触发者 | 时钟中断 | 线程自己 | 线程自己 |
| 状态变化 | Running → Ready | Running → Ready | Running → Blocked |
| 放回就绪队列？ | ✓（idle 放的） | ✓（idle 放的） | ✗ |
| 怎么回来 | 排队排到 | 排队排到 | 需外部 wakeup |
| 线程知情？ | 不知道 | 知道 | 知道 |
| 典型场景 | 时间片到了 | sched_yield() | futex_wait / sleep |

### 11. 完整故事：等锁 → 释放锁 → 被唤醒

```
线程 A: lock(mutex)
  → mutex 被 B 持有了
  → futex_wait(&mutex, 1)

  步骤:
  1. 检查 *&mutex == 1（确实还被持有着）
  2. FUTEX_QUEUES: 登记 A（key = {tgid, &mutex}）
  3. prepare_current_task_blocked():
       A.set_blocked()
       Scheduler.blocked_tasks.insert(A.tid, A)
  4. switch_to_next_task():
       handoff_current_to_idle(A) → __switch → idle
       idle: A 是 Blocked → publish_saved_handoff 不放回队列
       fetch_task → 选 C 跑

  ... A 在内核栈上冻结 ...

线程 B: unlock(mutex)
  → mutex = 0
  → futex_wake(&mutex, 1)

  步骤:
  1. FUTEX_QUEUES: 按 hash(&mutex) 找到桶，遍历找到 A
  2. complete_futex_wait(A.tid, Woken)
  3. wakeup_task(A.tid):
       Scheduler.blocked_tasks.remove(A.tid)
       A.set_ready()
       add_task(A)          → A 回到就绪队列
       kick_one_idle_hart() → 通知空闲 CPU

  ... 某 CPU 选中 A ...
  __switch → 恢复 A → ret 回到 switch_to_next_task 循环
  → current.is_running() == true → return
  → 回到 futex_wait → finish_futex_wait 返回 Woken → 返回 0
  → 回到 lock(mutex) → 获取锁成功，继续往下执行
```

A 从调 `futex_wait` 到返回，中间发生的所有切换对它来说只是一次"长暂停"——它的内核栈上保存的 `ra` 指向 `futex_wait` 内部，`ret` 回去后继续执行。它不知道中间经历了多少次 `__switch`、跑了多少个别的线程。

### 12. 本课只需牢记

1. `Blocked` 线程不在就绪队列，调度器看不见它，必须等外部唤醒。
2. `blocking_and_run_next()`：set_blocked → 放入 `blocked_tasks` → switch_to_next_task → 冻结。
3. `wakeup_task(tid)`：从 `blocked_tasks` 取出 → set_ready → 放回就绪队列。
4. `switch_to_next_task()` 的特点是唤醒后循环检查 `is_running()`，确认被叫醒才退出循环。
5. futex 线程同时存在于两处：FUTEX_QUEUES（记录等哪个地址）和 `blocked_tasks`（记录阻塞状态）。二者各司其职——futex_wake 查前者找到 tid，再把 tid 传给后者做调度唤醒。

### 13. 自测

1. `Blocked` 和 `Ready` 状态的区别是什么？`fetch_task` 会选中一个 `Blocked` 的线程吗？
2. `blocking_and_run_next()` 和 `preempt_current_task()` 的本质区别是什么？
3. 为什么线程不能自己唤醒自己？唤醒必须来自哪里？
4. FUTEX_QUEUES 和 `blocked_tasks` 分别存什么信息？为什么需要两个独立的结构？
5. 线程 A 调 `futex_wait(&addr, val)` 后，从阻塞到被 `futex_wake(&addr)` 唤醒，经历了哪些关键步骤？
6. 带超时的 futex_wait 如果超时了，谁负责发现并唤醒它？

<details>
<summary>参考答案</summary>

1. `Blocked` 在等某个条件，不在就绪队列中；`Ready` 已准备好运行，在就绪队列中等 CPU。`fetch_task` 只看就绪队列，永远不会选 Blocked 线程。
2. preempt 是被动抢占（时钟中断），线程状态 Run→Ready，放回就绪队列，下次继续跑。block 是主动阻塞（线程自己调用），状态 Run→Blocked，不在就绪队列中，必须有外部事件唤醒它。
3. 线程已是 Blocked 状态，CPU 不执行它的任何代码，所以无法自己唤醒自己。唤醒必须来自外部：另一个线程（futex_wake）、内核定时器（超时到期）、或信号（SIGKILL 等）。
4. FUTEX_QUEUES 记录 "tid → 在等哪个地址（futex key）"，按地址哈希索引，用于 `futex_wake` 查找。`blocked_tasks` 记录 "tid → TCB"，按 tid 索引，用于调度器管理。需要两个是因为一个线程可能不是通过 futex 阻塞的（比如纯定时睡眠），但调度器统一用 blocked_tasks 管理所有阻塞线程。
5. `futex_wait` → 检查 (*addr == val) → 登记 FUTEX_QUEUES → `prepare_current_task_blocked` → `switch_to_next_task` → handoff → __switch → idle... 冻结... 另一边 `futex_wake` → 查 FUTEX_QUEUES 找 tid → `complete_futex_wait`(Woken) → `wakeup_task`(tid) → 放回就绪队列 → fetch_task 选中 → `__switch` 恢复 → `switch_to_next_task` 循环退出 → futex_wait 返回 0。
6. 内核定时器定期触发 `check_futex_timeouts()`，扫描 `FUTEX_WAITS` 中超时的记录，发现过期的就调 `wakeup_task` 唤醒。线程醒来后 futex_wait 检测到完成原因是 TimedOut，返回 `-ETIMEDOUT`。

</details>
