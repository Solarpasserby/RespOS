# RespOS 全新系统调用实现工作流

本文用于比赛现场实现 Linux/POSIX 中不存在的官方自定义语义或全新系统调用。重点不是尽快让样例
“返回成功”，而是先把题面转换成可执行的 ABI 契约，再完成用户边界、状态归属、生命周期、并发和
双架构闭环。

对于 RespOS，RV64 和 LA64 的 trap 入口已经把系统调用统一整理为 `syscall(id, [usize; 6])`。除非题面
明确规定两种架构使用不同编号、布局或寄存器协议，新语义应实现于公共内核层，不应分别复制到两个
架构目录或四个平台实现中。

## 1. 先判断题型

### 1.1 已有系统调用增加新语义

例如给 `madvise` 增加自定义 advice、给 `fcntl` 增加 command、给 `ioctl` 增加 request，或给已有接口
增加 flag。这类题通常不新增系统调用编号，而是在现有 ABI 分派中增加一条经过完整校验的语义路径。

首先确认：

- 新值和已有 command/flag 是否冲突；
- 未知值是否继续返回原有 errno；
- 新状态属于线程、进程、open-file、inode、地址空间还是系统全局；
- 它与已有 flag 的组合、优先级和失败原子性；
- `fork/clone/exec/dup/close/exit` 后的继承和清理行为。

### 1.2 增加全新的系统调用

例如题面给出：

```c
long respos_watch(int fd, struct respos_watch *info, unsigned int flags);
```

这类题需要确认编号和 ABI，在 `os/src/syscall/mod.rs` 注册 dispatch，选择正确的领域模块实现状态机，
必要时增加用户态 raw wrapper，并用独立 probe 验证。

## 2. 把题面翻译成契约表

实现前先填写下表；不能确认的项目标为 `待验证`，不要默认为 Linux 中“相似接口”的行为。

| 项目 | 必须确认 |
| --- | --- |
| 编号 | RV64/LA64 是否相同，是否与现有编号冲突 |
| 参数 | 六个参数各自含义，寄存器顺序，signedness 和长度单位 |
| 用户指针 | 输入、输出或双向；NULL 和长度 0 是否允许 |
| 结构体 | `sizeof`、alignment、字段 offset、padding、版本字段 |
| flags/command | 合法位、组合限制、未知位的 errno |
| 返回值 | 成功值、部分成功、错误编码及是否返回新句柄 |
| 状态归属 | 线程、进程、fd entry、open-file、inode、MM 或全局对象 |
| 生命周期 | fork/clone/exec/dup/close/exit 后如何继承或销毁 |
| 并发 | 原子性、多个调用者的竞争和可见顺序 |
| 阻塞 | 等待条件、唤醒源、timeout、signal 和取消 |
| 错误顺序 | bad pointer、bad fd、bad flags、权限错误谁先返回 |
| 失败原子性 | 返回错误后，状态和输出缓冲区是否允许部分改变 |

自定义系统调用没有现成 Linux oracle，证据优先级为：

```text
官方题面
> 官方头文件和测试程序
> 官方样例输出
> 评分脚本的可观察要求
> 自己的推断
```

若题面确实允许参考一个类似的 Linux 接口，可以用 Linux probe 理解常见设计，但不能把相似接口的
未声明细节自动加入官方自定义契约。

## 3. 先写最小 probe

在写完整实现前，先准备一个只调用目标 syscall 的小型 C 或 Rust 程序。第一版至少闭合：

1. 一个最小合法调用；
2. 一个非法 flag/command；
3. 一个非法用户指针；
4. 返回值和 errno；
5. 调用前后的可观察状态。

随后补充隐藏测例最常见的边界：

- NULL、明显非法地址、跨页且第二页不可访问；
- 只读地址作为输出缓冲区；
- 长度 0、最大合法长度、加法或乘法溢出；
- 无效 fd、错误对象类型、已经关闭的对象；
- 重复调用和资源耗尽；
- 两线程并发，必要时跨进程并发；
- fork、clone、dup、exec、close 和 exit；
- 阻塞、signal、timeout、取消和多个 waiter；
- 部分成功后的返回数量、输出内容和后续状态。

每个 case 同时检查返回值、errno、输出缓冲区、对象状态和资源回收。probe 不要和内核共享同一份手写
结构体布局或错误常量，否则实现和测试可能在同一个错误上自洽。

## 4. RespOS 代码落点

### 4.1 编号与公共 dispatch

公共入口是 `os/src/syscall/mod.rs::syscall()`。先搜索编号和名称：

```bash
rg -n 'SYSCALL_目标名称|官方编号' os/src user/src
```

增加编号，并在 `match syscall_id` 中只做 ABI 解码：

```rust
const SYSCALL_RESPOS_WATCH: usize = /* 官方编号 */;

// syscall() 的 match 中：
SYSCALL_RESPOS_WATCH => sys_respos_watch(
    args[0],
    args[1] as *mut ResposWatch,
    args[2],
),
```

未注册编号应继续走现有 `ENOSYS`。不能为让程序继续执行而把未知编号或未知 command 统一返回成功。

### 4.2 选择正确模块

| 语义领域 | syscall 边界 | 状态机所有者 |
| --- | --- | --- |
| fd、文件、目录、inode | `os/src/syscall/fs.rs` | `os/src/fs/` |
| 进程、线程、调度 | `os/src/syscall/process.rs` | `os/src/task/` |
| 地址空间、页面、映射 | `os/src/syscall/mm.rs` | `os/src/mm/` |
| 网络 | `os/src/syscall/net.rs` | `os/src/net/` |
| 时间、定时器 | `os/src/syscall/time.rs` | timer/task 对象 |
| signal | `os/src/syscall/signal.rs` | signal/task 对象 |
| eventfd、epoll 一类 fd | `os/src/syscall/special_fd.rs` | 对应 FileOp/等待对象 |
| 独立新领域 | 新建 `os/src/syscall/xxx.rs` | 新建明确的领域模块 |

syscall 层只负责 ABI 解码、参数校验、用户拷贝、调用领域对象和 errno 映射。锁、等待队列、引用计数和
核心状态机不能长期堆在 dispatcher 中。

### 4.3 双架构边界

当前公共调用链是：

```text
RV64：a7=编号，a0..a5=参数 ┐
                             ├→ syscall(id, [usize; 6]) → 公共实现
LA64：r11=编号，r4..r9=参数 ┘
```

对应入口位于：

- `os/src/arch/rv64/trap/mod.rs`；
- `os/src/arch/loongarch64/trap/mod.rs`。

普通自定义 syscall 不应修改 trap。只有官方 ABI 明确要求不同寄存器、不同结构体布局或特殊返回协议时，
才引入最小的架构适配；板级目录 `os/src/platform/` 不承载 syscall 语义。

如需为仓库内 probe 增加 wrapper，可参考 `user/src/syscall.rs`：RV64 使用 `a7/a0..a5`，LA64 使用
`r11/r4..r9`。正式评分程序通常会直接按官方 ABI 发起 syscall，内核不能依赖仓库 wrapper 做参数修正。

## 5. 用户指针与结构体 ABI

统一使用 `os/src/mm/mod.rs` 提供的 `copy_from_user`、`copy_to_user`、`copy_cstr_from_user`、
`check_user_readable` 和 `check_user_writable`，禁止直接解引用用户指针。

长度计算必须检查溢出：

```rust
let bytes = count
    .checked_mul(core::mem::size_of::<Item>())
    .ok_or(Errno::EINVAL)?;
```

用户 ABI 结构体使用 `#[repr(C)]`，并在目标架构 probe 中检查 `sizeof`、`alignof` 和 `offsetof`。不要从
x86 布局推断 RV64/LA64；RespOS 已经发生过测试和内核共同采用错误 `epoll_event` 布局、专项自洽但真实
libc 失败的问题。

需要明确验证：

- 地址加长度是否溢出；
- 结构体或数组是否跨页；
- 输入只要求 readable，输出必须 writable；
- `count == 0` 时是否仍检查 NULL；
- 可变长度结构体怎样处理小版本、大版本和非零尾部；
- copyout 失败时已经完成的状态提交是否保留。

推荐把流程分成“读入用户数据 → 在内核缓冲区校验 → 执行领域操作 → 按契约 copyout”，不要持有
用户地址空间或领域大锁执行不受控 I/O。

## 6. 状态归属和生命周期

隐藏测例通常不只测一次正常调用，还会用继承和共享关系判断状态是否放错位置：

| 题面要求 | 常见正确位置 |
| --- | --- |
| 每线程独立 | TCB/thread state |
| fork 后复制 | 进程或地址空间状态 |
| `CLONE_VM` 后共享 | 共享 MM 或显式共享对象 |
| dup 后共享 | open-file description，而不是 fd table entry |
| 每次 open 独立 | `FileInner` 一类 open-file 状态 |
| 所有打开者共享 | inode 或后端对象 |
| mmap 与 read/write 一致 | PageCache/文件后端 |
| 全系统配置 | 有明确锁和权限边界的全局对象 |

实现前必须回答：fork 是否继承、clone 是否共享、exec 是否清除、dup 是否共享、最后一个引用关闭后何时
销毁、异常退出是否清理 waiter。若这些问题未确定，不要先用全局表临时保存状态。

## 7. 错误顺序和提交点

同样的 errno 集合，不同检查顺序也会被判错。将实现显式划成：

```text
复制和解析参数
→ 检查 flags、长度和结构体版本
→ 查找 fd/对象并检查类型与权限
→ 准备资源或 waiter
→ 最后一次条件复检
→ 不可逆提交
→ copyout/返回
```

具体顺序以官方契约为准。例如 bad pointer、bad fd 和权限错误谁优先，不能凭“先判权限更安全”决定。
在不可逆提交点之前失败时应保持状态不变；提交后的 copyout 失败是否回滚，同样必须由题面或 probe
确定。若 syscall 能部分处理数组，还要确认返回已处理数量还是直接返回 errno。

## 8. 阻塞、signal 和并发

可能等待条件的 syscall 应采用防丢唤醒协议：

```text
检查条件
→ 注册 waiter
→ 再次检查条件
→ 睡眠
→ 由事件、timeout、signal 或关闭动作唤醒
→ 注销 waiter
→ 重新检查并决定返回
```

不能用无界 `yield` 轮询代替等待队列。需要逐项确定：

- timeout 是相对时间还是绝对时间，零值代表 poll 还是永久等待；
- signal 返回 `EINTR`、部分结果还是重新开始；
- 是否支持 `SA_RESTART`；
- 多个 waiter 唤醒一个还是全部，谁是唯一成功者；
- close、exit、对象销毁是否唤醒等待者；
- SMP 下检查条件与修改状态是否在同一同步协议内。

只有契约明确允许重启时，才把新编号加入 `os/src/syscall/mod.rs::is_restartable_syscall()`。不能仅因为
接口会阻塞就默认可重启。

## 9. 现场 90 分钟推进表

### 0～15 分钟：冻结契约

- 保存题面、头文件、样例、评分脚本和 SHA-256；
- 确认编号并用 `rg` 排除冲突；
- 填写 ABI 契约表；
- 确定状态所有者、生命周期和不可逆提交点；
- 把歧义标为 `待验证`，不要同时实现多个猜测版本。

### 15～35 分钟：最小调用闭环

- 写 raw syscall probe；
- 注册编号和 dispatch；
- 实现一个正常 case、一个非法参数和一个 `EFAULT`；
- 确认参数排列、返回值和 errno 编码正确；
- 完成目标架构快速构建与首次 guest 运行。

### 35～60 分钟：完整语义

- 将状态放入正确领域对象；
- 完成失败原子性和资源回收；
- 完成 fork/clone/exec/dup/close/exit 规则；
- 如会阻塞，完成 waiter、signal、timeout 和关闭唤醒。

### 60～75 分钟：主动攻击实现

- 跨页和只读用户指针；
- 长度和地址溢出；
- 未知 flag 与错误优先级；
- 重复调用、两线程/两进程竞争；
- 部分成功和异常退出后的状态。

### 75～90 分钟：双架构交付

```text
最小 probe
→ 官方样例
→ 官方完整任务
→ RV64
→ LA64
→ 相邻 subsystem 回归
→ 仓库门禁
→ 保存证据并提交
```

若 45 分钟后仍不能回答“状态属于谁”或“错误后是否已经生效”，停止扩大实现，回到题面、样例和评分
脚本。继续堆分支通常只会放大返工。

## 10. 构建、验证与证据

修改前先查相关历史和已确认陷阱：

```bash
rg -n '目标符号|相关 errno|官方编号' os/src user/src docs/codex
git log -S'目标符号' --all --oneline
git blame os/src/相关文件.rs
```

按成本递增验证，上一层失败就不要先跑完整回归：

1. 契约表和 probe 预期明确；
2. 目标模块编译或单架构快速构建；
3. 目标架构 guest 专项；
4. 官方样例和完整任务；
5. 另一架构相同 probe 和任务；
6. 受影响的 task/MM/FS/net/signal 相邻回归；
7. 提交门禁。

当前顶层构建和门禁入口：

```bash
make build-qemu-rv64
make build-qemu-loongarch64
git diff --check
make check-repo-layout
make preflight
git status --short
```

RV64/LA64 构建共享生成的 Cargo config，不要并行执行。`make preflight` 适合修改稳定后的交付检查，不适合
每轮小编辑。运行命令、镜像和 QEMU 参数以 `docs/codex/workflows.md` 的当前记录为准。

保存证据时至少记录：当前 commit、工作区状态、题面/头文件 hash、架构、镜像 hash、完整命令、退出码、
原始日志和 probe 源码。不要把凭据、比赛私密材料或大体积镜像提交到仓库。

## 11. 最终检查表

- [ ] 编号无冲突，两架构的编号和调用约定已经确认；
- [ ] 结构体使用 `#[repr(C)]`，尺寸、对齐和字段偏移已经验证；
- [ ] 未直接解引用用户指针，长度和地址运算不会溢出；
- [ ] 未知 flags/command 被按契约拒绝；
- [ ] errno、错误优先级和部分成功符合契约；
- [ ] 不可逆提交点清晰，失败后没有意外半提交；
- [ ] 状态属于正确对象；
- [ ] fork/clone/exec/dup/close/exit 行为明确；
- [ ] 阻塞调用没有丢失唤醒，signal/timeout/关闭路径已经验证；
- [ ] SMP 下没有检查—执行竞态，资源最终能够回收；
- [ ] 公共语义没有复制到架构或平台分支；
- [ ] RV64、LA64 的当前专项和官方任务均有日志证据；
- [ ] 相邻功能没有回归，临时 trace 已删除；
- [ ] `git diff --check`、仓库布局检查和交付门禁通过。

现场记忆句：**先把题面变成契约和 probe，再注册 ABI；syscall 层只守边界，状态放到真正的所有者；
最后用错误、生命周期、并发和双架构测试主动攻击自己的实现。**
