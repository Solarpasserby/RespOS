# 离线资料归档清单

本地离线包建议放在仓库根目录的 `offline/`；该目录已被 Git 忽略，不进入源码包。是否允许携带或导入
这些材料，必须以最新官方规则为准。不要把“本地能保存”误解成“赛场一定能使用”。

## 建议目录

```text
offline/
├── MANIFEST.md                 # 来源、版本、用途、许可证、获取日期
├── SHA256SUMS                  # 所有不可再生文件的校验值
├── repo/                       # Git bundle、已验证源码包、补丁
├── images/                     # 官方压缩镜像、rootfs、辅助盘模板
├── toolchains/                 # Rust、交叉编译器、QEMU、CMake 等离线安装材料
├── cargo/                      # 合规的 registry/git 缓存或 vendor 依赖
├── containers/                 # 可选的已验证开发容器导出
├── specs/                      # Linux UAPI、ELF/ISA/工具官方文档
├── tests/                      # 官方测试、最小 probe、Linux baseline
├── logs/                       # 少量已验证基线日志与故障样例
└── restore/                    # 恢复顺序、环境清单和验证命令
```

实际大文件不进 Git；仓库内只维护本手册和必要的小型、可审查脚本。

## 值得保存的内容

| 类别 | 建议内容 | 注意事项 |
| --- | --- | --- |
| 仓库 | 当前主线 bundle、最终源码包、SHA-256、关键提交号 | bundle 可能包含完整历史，先确认无敏感 refs |
| 镜像 | 官方原始压缩包、已验证 rootfs、对应校验值 | 原件只读；运行副本与原件分开 |
| 环境 | Dev Container 定义、容器镜像导出、OS/CPU/磁盘清单 | 容器可能很大；必须实际做一次无网恢复 |
| Rust | 固定 nightly、双架构 target、rust-src、llvm-tools | 当前仓库固定 `nightly-2025-01-18`；保存许可证和来源 |
| C/C++ | 两架构 musl 交叉编译器、binutils、CMake、e2fsprogs | 记录精确版本和动态库依赖 |
| QEMU/GDB | 两架构 QEMU、对应 GDB、固件/bootloader | 记录 `--version` 与运行参数 |
| Cargo 依赖 | registry/git 缓存或合规 vendor 快照 | 不要只验证“缓存存在”，要断网构建 |
| 规范 | Linux man-pages/UAPI、ELF gABI、RISC-V/LoongArch 官方文档 | 尊重许可证；优先保存官方版本和发布日期 |
| 测试 | 官方脚本、测试清单、Linux 对照 probe、baseline | 记录架构、libc、内核版本和预期输出 |
| 证据 | 最近已验证的双架构日志、已知故障样例、性能基线 | 每份日志绑定 commit、镜像、命令、日期 |
| 展示材料 | PDF/PPT、演示命令、备用录屏、字体 | 现场展示与提测材料分开 |

还可以保存一份“恢复演练报告”：在另一台机器断网，从零恢复后记录缺了什么、耗时多久。它通常比再
复制一份泛用教程更能暴露真实风险。

## 创建仓库备份

仅备份当前主线和标签：

```bash
mkdir -p offline/repo
git bundle create offline/repo/RespOS-main.bundle main --tags
git bundle verify offline/repo/RespOS-main.bundle
sha256sum offline/repo/RespOS-main.bundle
```

若现场工作不在 `main`，把实际分支名显式加入命令。不要无意识使用 `--all`，它可能把私有实验分支、
旧凭据或不希望分发的历史一起装入 bundle。

最终源码包应从已提交、干净、通过门禁的 HEAD 生成：

```bash
make package-submit
```

该命令本身会复验并在 `dist/` 生成源码包与校验文件。现场修改尚未提交时不要为了满足 clean gate 而
丢弃修改。

## 环境清单

在 `offline/restore/environment.txt` 中保存以下命令的输出即可，不要保存整份 home 目录：

```bash
uname -a
rustup show
rustc -Vv
cargo -V
qemu-system-riscv64 --version
qemu-system-loongarch64 --version
cmake --version
riscv64-linux-musl-gcc --version
loongarch64-linux-musl-gcc --version
```

同时记录磁盘容量、内存、CPU 数、容器/虚拟化版本以及工具实际路径。环境清单是诊断证据，不是可恢复
备份；仍需保存安装包、容器或缓存并做离线演练。

## 生成校验清单

进入 `offline/` 后，对需要长期保存的文件生成清单；不要把 `SHA256SUMS` 自己包含进去：

```bash
find . -type f ! -name SHA256SUMS -print0 \
  | sort -z \
  | xargs -0 sha256sum > SHA256SUMS
sha256sum -c SHA256SUMS
```

每次替换文件后重新生成并复验。至少保留两份物理独立副本，并从副本实际恢复一次；前提仍是比赛规则
允许携带相应介质。

## 不应保存或提交的内容

- SSH 私钥、token、cookie、账号密码、云服务凭据和个人身份材料；
- `~/.codex`、聊天原文、会话数据库、浏览器 profile 等私人状态；
- 未确认许可证允许分发的第三方源码、PDF、二进制和数据集；
- 仅凭文件名无法追溯来源的镜像、工具链和“最新版”压缩包；
- 大量重复构建目录、可重建中间产物和无上下文的临时日志；
- 含敏感历史的 `git bundle --all`、home 目录镜像或整机备份。

提交前执行 `git status --short` 和 `git ls-files offline img`，确认离线材料没有误入仓库。密钥即使从
Git 删除也可能仍留在历史中；一旦误提交，应立即吊销并按安全流程清理，不能只补一个删除提交。
