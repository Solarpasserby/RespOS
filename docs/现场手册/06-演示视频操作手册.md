# RespOS 演示视频操作手册

目标是在 **RespOS 启动的 RISC-V Linux ABI 用户环境内**，连贯展示：

1. 从 GitHub 克隆 RespOS；
2. 查看真实提交历史；
3. 用全屏 Vim 修改并保存 `README.md`；
4. 使用镜像内的 Cargo/rustc 编译刚刚克隆的 RespOS 内核；
5. 检查新生成的内核产物。

本文按本地提交 `15336713`、2026-08-18 的仓库结构整理。演示前必须重新记录实际提交，不要把本文中的
哈希当成永久值。当前方案优先选 RV64：已有完整的 guest 自举证据，预计资源和等待时间也比 LA64 更
容易控制。

## 对外表述

推荐说：

> RespOS 启动了真实的 Linux 用户态开发环境。在这个由 RespOS 提供系统调用、文件系统、进程、内存、
> 网络和终端能力的环境里，我们从 GitHub 克隆项目，用 Vim 修改源码仓库，再由 Cargo 调用 rustc 编译
> 当前 RespOS 内核。

不要说“RespOS 从零自举了 Rust 工具链”。rustc、Cargo、CMake 和交叉工具链是根镜像预装的；RespOS
负责让这些真实工具在其 Linux ABI 上运行，并用它们从源代码生成新的内核。这属于 guest 内内核自编译，
不是从源码重建编译器的完全自举。

## 当前两个硬前置

### 1. 远端必须包含准备展示的提交

截至本文整理时，本地 `main` 为 `15336713`，`origin/main` 为 `8ad76b82`，远端落后两个提交。未经项目
负责人确认和推送，队友直接 clone 得不到当前本地版本。

录制负责人在宿主机执行：

```bash
git status --short
git rev-parse HEAD
git rev-parse origin/main
git rev-list --left-right --count origin/main...HEAD
git log --oneline origin/main..HEAD
```

应先完成内部审查，再由有权限的人正常推送。本文不要求强推，也不要为了视频改写共享历史。推送后验证：

```bash
git fetch origin
test "$(git rev-parse HEAD)" = "$(git rev-parse origin/main)"
git ls-remote https://github.com/Solarpasserby/RespOS.git refs/heads/main
```

把最终 40 位哈希抄进提词卡。视频中的 `git rev-parse HEAD` 应与它一致。

### 2. guest 必须有仓库固定的 Rust 工具链

当前仓库正式构建固定 `nightly-2025-01-18`，决赛 RV64 根镜像预装的是
`nightly-2026-05-28`。历史 bootstrap 成功结果早于这次固定工具链调整，不能直接证明当前 HEAD 会在未
准备的镜像中重建。

推荐在启动 QEMU 后、正式录屏前，在同一次 guest 会话中安装精确工具链：

```bash
rustup toolchain install nightly-2025-01-18 \
  --profile minimal \
  --component rust-src,llvm-tools-preview \
  --target riscv64gc-unknown-none-elf
rustc +nightly-2025-01-18 --version
rustup target list --toolchain nightly-2025-01-18 --installed
```

正式录制前至少用当前提交完整彩排一次。QEMU 使用 `-snapshot`，退出后安装和编辑都会丢失；因此工具链
准备、彩排清理和正式录制应尽量在同一次 QEMU 启动中完成。

## 宿主机准备

### 资源和文件

- 建议至少给 guest 8 GiB 内存、4 个 hart；宿主机同时不要运行另一架构 QEMU。
- 确认 `img/sdcard-rv-pub.img` 存在且有足够磁盘空间。
- 确认当前源码能完成 `make build-qemu-rv64`。
- 关闭终端通知、输入法浮窗和会泄露个人信息的窗口。
- 终端建议 120×36 以上，字体清晰；提前关闭彩色、超长 shell prompt。

检查命令：

```bash
git status --short
git rev-parse --short=12 HEAD
rustc --version
qemu-system-riscv64 --version | head -n 1
df -h . /tmp
make build-qemu-rv64
```

启动交互诊断环境：

```bash
make run-rv-diagnostic \
  RV_DIAGNOSTIC_MEM=8G \
  RV_DIAGNOSTIC_SMP=4 \
  RV_DIAGNOSTIC_OUTPUT=/tmp/respos-demo-rv.log
```

该入口使用决赛根镜像、virtio-net 和 `-snapshot`，不会把演示修改写回官方原始镜像。看到：

```text
[contest_launcher] diagnostic mode: starting embedded user shell
Rust user shell
/> 
```

输入绝对路径启动镜像内 Bash：

```bash
/bin/bash
```

进入 Bash 后先准备环境：

```bash
export HOME=/root
export TMPDIR=/tmp
export PATH=/root/.cargo/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
export RUSTUP_HOME=/root/.rustup
export CARGO_HOME=/root/.cargo
export LC_ALL=C
export TERM=xterm
cd /tmp
```

检查网络和工具，但这部分通常不录或后期加速：

```bash
uname -a
git --version
vim --version | head -n 2
rustc --version
cargo --version
getent hosts github.com
git ls-remote https://github.com/Solarpasserby/RespOS.git refs/heads/main
```

若精确 Rust 工具链尚未安装，按上一节安装。安装完成后不要退出 QEMU。

## 正式录制脚本

下面命令由队友逐条输入。不要整段粘贴，否则看不清每项能力。

### 镜头一：确认运行在 RespOS

```bash
clear
uname -a
cat /proc/cpuinfo | head -n 20
pwd
```

讲解：当前 shell、Git、Vim 和 rustc 都是运行在 RespOS 内的真实用户程序，不是宿主机命令。

### 镜头二：克隆当前仓库

```bash
cd /tmp
git clone --single-branch --branch main --depth 20 \
  https://github.com/Solarpasserby/RespOS.git RespOS-demo
cd RespOS-demo
git status --short --branch
git rev-parse HEAD
```

预期：clone 成功，工作区干净，`HEAD` 与提词卡中的远端 main 哈希一致。如果哈希不一致，停止录制，先
解决远端分支或缓存问题，不要继续假装展示的是当前版本。

### 镜头三：查看提交历史

```bash
git log -5 --oneline --decorate
git show -1 --stat --oneline
```

讲解：这是刚从远端取得的真实 Git 历史。因为演示使用 `--depth 20`，这里只保留最近 20 个提交；不要把
它表述成完整仓库历史。如果希望展示完整历史，录制前去掉 `--depth 20` 并重新评估 clone 时间。

### 镜头四：用 Vim 修改 README

```bash
vim -Nu NONE -n README.md
```

建议按键流程：

1. 输入 `gg` 回到首行；
2. 输入 `o` 在下一行新建一行；
3. 输入 `<!-- edited with Vim inside RespOS -->`；
4. 按 `Esc`；
5. 输入 `:wq` 并回车。

退出 Vim 后验证修改确实落盘：

```bash
git status --short
git diff -- README.md
```

不要在演示仓库中提交或推送这行临时文字。`git diff` 能同时证明 Vim 保存成功和 Git 正确观察到修改。

### 镜头五：用 rustc 编译 RespOS 内核

先证明工具链版本与目标：

```bash
rustc +nightly-2025-01-18 --version
rustup target list --toolchain nightly-2025-01-18 --installed \
  | grep riscv64gc-unknown-none-elf
```

使用 debug 模式缩短视频等待时间；它仍会完整编译用户程序、lwext4 和 RespOS 内核：

```bash
time make build-qemu-rv64 RV_MODE=debug 2>&1 | tee /tmp/respos-demo-build.log
```

构建期间可以加速或剪辑，但画面应保留：

- `Compiling` 输出；
- `cargo build`/rustc 所在的构建阶段；
- 命令最终返回成功；
- 实际生成的 `kernel-rv`。

构建结束后验证：

```bash
test -s kernel-rv
file kernel-rv
sha256sum kernel-rv
rust-readobj -h -l kernel-rv | grep -E 'Format:|Arch:|AddressSize:|Entry:'
tail -n 20 /tmp/respos-demo-build.log
```

推荐讲解：`make` 只是仓库的构建编排入口，Rust 源码实际由 Cargo 调用 rustc 编译；最终产物是新的
RISC-V 64 RespOS 内核 ELF。README 的临时改动不影响内核代码，但证明 clone 后的工作区可被真实编辑。

## 结束录制

保留最后一个画面约 3 秒，至少包含：

- `file kernel-rv` 的 RISC-V ELF 结果；
- `sha256sum kernel-rv`；
- shell prompt 正常返回。

然后执行：

```bash
exit
```

回到 RespOS 内嵌 shell 后：

```text
quit
```

`quit` 会让 guest 正常关机。紧急退出 QEMU 可使用 `Ctrl-a` 后按 `x`；这只作为卡死备用，不用于正常
收尾。

## 彩排清理与二次录制

在同一次 QEMU 会话里完成工具链安装和彩排后，可以删除演示 checkout，再开始正式录制：

```bash
cd /tmp
rm -rf /tmp/RespOS-demo
clear
```

这里的删除目标是明确的 guest 临时目录。执行前必须确认 `pwd` 和路径，不能写成模糊通配符。退出 QEMU
后 `-snapshot` 也会丢弃全部改动。

## 常见故障与备用方案

| 现象 | 先检查 | 处理 |
| --- | --- | --- |
| clone 报 DNS 错误 | `cat /etc/resolv.conf`、`getent hosts github.com` | 应有 `nameserver 10.0.2.3`；重新启动诊断入口并确认 virtio-net 上线 |
| GitHub HTTPS 证书错误 | 系统时间、CA 文件 | 检查 `date` 与 `/etc/ssl/certs/ca-certificates.crt`，禁止用 `-k` 绕过 |
| clone 的提交不是本地 HEAD | 宿主 `origin/main...HEAD` | 先确认并正常推送；不要在 guest 里伪造 commit |
| Vim 无法正常全屏 | `TERM=xterm`、终端尺寸 | 重新导出 TERM；仍失败时停止录制，不用批处理冒充全屏编辑 |
| make 提示缺少 nightly-2025 | `rustup toolchain list` | 在本次 guest 会话安装精确工具链后重新开始 |
| 构建非常慢 | 内存、SMP、宿主 QEMU 优先级 | 保持单个 QEMU、8 GiB/4 hart；正式视频对等待段做加速，不并行启动 LA |
| `No space left on device` | `df -h /tmp /` | 清理 `/tmp/RespOS-demo` 后重来；不要修改或扩容官方原镜像 |
| 构建失败但旧 `kernel-rv` 存在 | 命令退出码与产物时间 | clone 后先确认目录无旧产物；只有本轮命令成功才展示产物 |

如果现场无法下载固定工具链，不建议临时改 Makefile 后仍宣称“按当前正式配置构建”。可以把视频拆成两段：
软件镜像展示 clone/log/Vim/rustc hello world，已准备的 bootstrap 录像展示内核自编译；解说中明确边界。
