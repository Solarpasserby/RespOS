# RespOS 新软件兼容工作流

本工作流用于现场拿到一个此前未运行过的软件、源码工程或官方自定义 syscall 后，尽快获得可靠证据、
定位第一个阻断并完成最小正确修复。目标不是让程序“看起来启动”，而是满足题目要求的可观察结果、
退出状态、产物和失败语义。

## 总流程

```text
冻结题目与环境
→ 静态检查 ELF、解释器和依赖
→ 在 RespOS 固定首个失败
→ 在 Linux 建立对照或按自定义契约写 probe
→ 归类到 ELF / syscall / MM / task / FS / network
→ 最小正确修复
→ 专项 probe
→ 原软件复测
→ 双架构与相邻回归
→ 保存证据并提交
```

任何时候都优先处理第一个稳定失败。后续几十条 `ENOENT`、`TBROK`、超时或崩溃可能只是前一个初始化
错误的级联。

## 0. 三人现场分工

| 角色 | 第一任务 | 不应同时做的事 |
| --- | --- | --- |
| A：复现与证据 | 保存题面、版本、日志，缩成最小命令 | 未确认首错前不断换参数 |
| B：Linux 对照 | 同架构/同 libc 跑 `strace` 和最小 probe | 把其他架构或不同 libc 结果直接当契约 |
| C：源码定位 | 沿调用链定位实现边界，准备最小补丁 | 在没有契约时一次补多个“猜测 syscall” |

只有一人时也按 A → B → C 顺序执行。每 15 分钟同步一次：当前首错、已排除项、下一项单变量实验。

## 1. 冻结输入和证据

先建立本地记录，建议复制[现场故障记录模板](05-现场故障记录模板.md)。至少记录：

```bash
git status --short
git rev-parse HEAD
git log -3 --oneline --decorate
sha256sum /path/to/root.img /path/to/software 2>/dev/null
file /path/to/software
```

还要记录：题目原文、软件来源和版本、架构、libc、完整命令、环境变量、QEMU 内存/SMP、超时、期望
结果以及完整原始日志。不要只保存截图，也不要用历史成绩代替当前 HEAD 证据。

若软件由压缩包、Git 仓库或 APK/DEB 提供，保留原件和 SHA-256；实验使用副本。不要直接修改官方根
镜像，QEMU 入口保持 `-snapshot`。

## 2. 静态检查：程序还没运行前

在可信的宿主 Linux 上检查二进制：

```bash
file ./program
readelf -h ./program
readelf -l ./program | grep -E 'INTERP|Requesting program interpreter|LOAD'
readelf -d ./program | grep -E 'NEEDED|RPATH|RUNPATH'
readelf -Ws ./program | grep -E 'GLIBC_|MUSL_' | tail -n 30
```

回答以下问题：

- 架构是 RV64 还是 LA64，endianness 和 ELF class 是否正确？
- 静态链接还是动态链接？`PT_INTERP` 要求哪个 loader？
- 所需 `.so` 是否存在，版本符号是否超出镜像 libc？
- 入口和 LOAD segment 的文件偏移、虚拟地址、权限是否合理？
- 程序、解释器和库是否有执行/读取权限？

`execve()` 返回 `ENOENT` 不一定是程序文件不存在，也可能是 `PT_INTERP` 指向的动态加载器缺失。不要
在来源不可信的二进制上随意运行 `ldd`；优先使用不会执行目标程序的 `readelf`。

检查镜像内文件时优先只读：

```bash
debugfs -R 'stat /lib/ld-musl-riscv64.so.1' img/目标镜像.img
debugfs -R 'ls -l /lib' img/目标镜像.img
```

实际 loader 路径以 ELF `PT_INTERP` 为准，不能照抄示例。

## 3. 在 RespOS 固定首个失败

先运行最小入口，不要直接上完整 workload：

```bash
./program --version
./program --help
timeout 30 ./program 最小参数
echo "exit=$?"
```

保存从启动到第一处异常的完整串口输出。判断：

- 是否成功进入 `main`；
- 是明确 errno、signal、panic、超时，还是输出/产物错误；
- 单核/多核是否不同；
- RV/LA 是否相同；
- 重复 3 次是否稳定。

“能打印 help”只能证明 loader 和一小部分 libc 路径可用，不代表核心功能兼容。成功判据必须包含题目
要求的输出、文件、网络结果和退出码。

## 4. 建立 Linux oracle

标准 Linux ABI 问题尽量在相同架构、相同 libc 和相同软件版本上对照：

```bash
strace -ff -yy -s 256 -o /tmp/software.strace \
  timeout 30 ./program 最小参数
echo "exit=$?"
rg -n 'ENOSYS|EINVAL|EFAULT|EPERM|EACCES|ENOENT|EINTR' /tmp/software.strace*
```

RespOS guest 不应假设具备完整 ptrace/strace；`strace` 主要在 Linux oracle 使用。对比的是 syscall 参数、
返回值、errno、调用顺序和提交后状态，不是要求 RespOS 复制 Linux 内部实现。

把复杂失败缩成几十行 C/Rust probe，至少覆盖：

- 正常路径；
- NULL、非法指针、跨页和只读 copyout；
- 长度 0、边界值和过大值；
- 精确 errno 与错误优先级；
- 失败前后状态是否变化；
- 阻塞、signal、timeout 和并发唤醒；
- 重复调用和资源回收。

若题目是官方自定义 syscall，Linux 不存在对应 oracle。此时题面、头文件、样例和评分脚本是契约；先
把每条可观察要求转成 probe，再实现内核。

## 5. 按症状分流

| 首个症状 | 优先检查 | RespOS 入口 |
| --- | --- | --- |
| `Exec format error` | 架构、ELF class、header | `os/src/mm/memory_set.rs` ELF loader |
| 文件存在但 exec `ENOENT` | `PT_INTERP`、loader、symlink | loader + `os/src/fs/namei.rs` |
| `ENOSYS` | syscall 编号、ABI、dispatch | `os/src/syscall/mod.rs` |
| errno 不同 | 检查顺序、权限、失败原子性 | 对应 `os/src/syscall/*.rs` |
| SIGSEGV/SIGBUS | PC、fault addr、VMA、权限、EOF | arch trap → `MemorySet::handle_page_fault` |
| 卡死/超时 | 最后阻塞 syscall、waiter、timer、signal | `os/src/task/`、futex、pipe、socket |
| 写后读旧值/文件损坏 | File/inode/PageCache identity、writeback | `os/src/fs/`、`os/src/mm/` |
| DNS/HTTP/Git 失败 | virtio-net、DNS、TCP、TLS | [QEMU 网络手册](08-QEMU网络使用手册.md) |
| 只在一个架构失败 | trap frame、结构体布局、页表/TLB | `os/src/arch/{rv64,loongarch64}/` |
| 只在一个平台失败 | MMIO、设备、根盘、启动策略 | `os/src/platform/` |

详细故障树见[故障树与源码地图](01-故障树与源码地图.md)。

## 6. 新增或修复 syscall

### 标准 Linux syscall

1. 从目标架构 Linux UAPI 和真实 probe 确认编号、类型、flag、结构体布局及 errno。
2. 在 `os/src/syscall/mod.rs` 增加或核对编号与 dispatch。
3. syscall 层只做 ABI 解码、用户拷贝和 errno 映射；状态机放入 task/MM/FS/net 领域模块。
4. 明确不可逆提交点，copyout 失败时按 Linux 行为决定保留还是回滚。
5. 阻塞接口明确 waiter 注册、条件复检、signal interruption、restart 和 timeout。
6. 写最小 probe，再运行原软件。

### 官方自定义 syscall

全新接口的详细契约表、RespOS 代码落点、阻塞协议、90 分钟时间盒和交付检查表见
[全新系统调用实现工作流](10-全新系统调用实现工作流.md)。本节只保留快速分流入口。

先整理一张契约表：

| 项 | 必须明确 |
| --- | --- |
| 编号 | 两架构是否相同，是否与已有编号冲突 |
| 参数 | 每个寄存器含义、signedness、指针方向、长度单位 |
| 结构体 | size、alignment、padding、版本字段 |
| 返回值 | 成功值、部分成功、错误编码 |
| 状态 | 作用于线程、进程、fd、inode 还是全局对象 |
| 并发 | 原子性、阻塞条件、唤醒和取消 |
| 生命周期 | 创建、引用、关闭、exit/exec/fork 后行为 |

不要为了让测例继续而对未知操作直接返回成功，也不要把自定义 ABI 硬塞进板级模块。除非题面明确区分
平台，否则 syscall 语义应位于公共层，两架构仅负责寄存器/trap 机制。

### 用户指针边界

统一使用 `os/src/mm/mod.rs` 的 `copy_from_user`、`copy_to_user` 和 C 字符串辅助函数，不直接解引用用户
指针。检查长度乘法溢出、跨页、部分可访问区间和写权限。pathname 限制不能复用于 `exec argv/envp`。

更多检查项见[Linux ABI 高频语义](02-Linux-ABI高频语义.md)。

## 7. 最小修复原则

- 修首个根因，不批量加入假实现。
- 一次提交只闭合一条可解释调用链。
- 保持平台差异在 `os/src/platform/`、ISA 差异在 `os/src/arch/`。
- 普通文件 buffered I/O 与 `MAP_SHARED` 继续共用 PageCache。
- 不在 MM 大锁内新增不受控后端 I/O。
- 不用 `yield` 轮询替代 pipe/socket/futex/wait 的事件唤醒。
- 不用历史 LTP 分数证明当前修改正确。
- 临时 trace 必须 feature 化或在交付前删除；不能让串口输出显著改变性能结论。

修改前先查历史：

```bash
rg -n '目标符号|相关 errno' os/src docs/codex
git log -S'目标符号' --all --oneline
git blame os/src/相关文件.rs
```

[`docs/codex/pitfalls.md`](../codex/pitfalls.md) 中已有大量类似根因，优先复用已确认的不变量。

## 8. 分层验证

按成本从低到高推进，上一层失败就不进入下一层：

1. Linux oracle 与最小 probe 预期明确；
2. `cargo check` 或目标模块快速构建；
3. RV64 和 LA64 内核构建；
4. 目标架构 guest 中运行 probe；
5. 原软件最小任务；
6. 原软件完整题目任务；
7. 另一架构相同任务；
8. 相邻 subsystem 回归；
9. 提交门禁。

常用命令：

```bash
make build-qemu-rv64
make build-qemu-loongarch64

make run-rv-software RV_SOFTWARE_OUTPUT=/tmp/respos-rv-new-software.log
make run-la-software LA_SOFTWARE_OUTPUT=/tmp/respos-la-new-software.log

git diff --check
git status --short
make preflight
```

不要并行运行 RV/LA 构建：两者共享生成的 Cargo config。`make preflight` 会完整重建，适合修改稳定后，
不适合每个编辑循环。

## 9. 现场时间盒

### 前 15 分钟

- 保存题面、文件和 hash；
- `file/readelf`；
- 在 RespOS 跑 `--version/--help/最小任务`；
- 固定第一个失败；
- 分派 Linux oracle 与源码入口。

### 15～45 分钟

- 形成最小 probe；
- 确认 ABI 契约；
- 实施一个最小修复；
- 完成单架构专项。

### 45～90 分钟

- 原软件复测；
- 另一架构构建和运行；
- 补相邻回归；
- 整理日志、截图、提交说明。

若 30 分钟仍没有稳定首错，应停止扩大修改，回到 ELF/依赖/环境和测试框架。若修复只能靠返回假成功，
应保留当前可得分子项并明确阻断，避免破坏已有功能。

## 10. 完成定义

一个软件兼容任务只有同时满足以下条件才算完成：

- 题目规定的实际功能、输出、文件或网络结果正确；
- 进程退出码正确，无 kernel panic、残留任务或后续污染；
- 最小 probe 能解释修复的 Linux/题面契约；
- 失败路径 errno 和状态提交合理，不是假成功；
- 要求的平台/架构均有当前 commit、镜像、命令和日志证据；
- `git diff --check` 通过，工作区中没有误入镜像、密钥和临时日志；
- 可由队友从记录中的第一条命令复现。

提交前把稳定架构事实、设计决定、当前验证结果或新坑分别更新到 `docs/codex/architecture.md`、
`decisions.md`、`current-status.md` 或 `pitfalls.md`，不把聊天记录和未经验证的猜测写进项目知识。
