# 故障树与源码地图

## 先分流

```text
不能启动
├─ 没有任何串口输出 → 产物/装载地址/固件/平台入口
├─ 早期 panic       → arch + platform + 初始化顺序
└─ 进入用户态前停住 → 根盘/挂载/init/ELF loader

用户程序失败
├─ SIGSEGV/SIGBUS → trap → MemorySet → VMA/PTE/COW/PageCache/ELF
├─ syscall errno  → syscall dispatch → 参数拷贝 → 领域实现 → copyout
├─ 卡死/超时      → scheduler/wakeup/timer/futex/pipe/socket/wait
└─ 文件不一致     → fd → File → namei/inode → PageCache → ext4/writeback
```

不要从最后一条错误开始。先保存从启动到首个异常之间的完整串口日志，并记录它发生前最后一个成功
阶段。只有一个架构失败时，先核对架构和平台层；两个架构同样失败时，优先查公共语义。

## 四个平台边界

| 平台 | 架构机制 | 板级实现 | 构建入口 |
| --- | --- | --- | --- |
| QEMU RV64 | `os/src/arch/rv64/` | `os/src/platform/qemu_rv64.rs` | `make build-qemu-rv64` |
| JH7110 / VisionFive 2 | `os/src/arch/rv64/` | `os/src/platform/jh7110.rs` | `make build-jh7110` |
| QEMU LoongArch64 | `os/src/arch/loongarch64/` | `os/src/platform/qemu_loongarch64.rs` | `make build-qemu-loongarch64` |
| LS2K1000 | `os/src/arch/loongarch64/` | `os/src/platform/ls2k1000.rs` | `make build-ls2k1000` |

`os/src/platform/mod.rs` 是 `board_*` feature 的唯一选择点。ISA 页表、trap 和上下文切换放在
`os/src/arch/`；设备枚举、MMIO、启动/关机和根盘策略放在 `os/src/platform/`。不要把新板级分支
散回公共 MM、FS 或 task 代码。

## 高频调用链

### 系统调用

```text
用户 ecall/syscall
→ os/src/arch/{rv64,loongarch64}/trap/mod.rs
→ os/src/syscall/mod.rs::syscall
→ os/src/syscall/{process,fs,mm,signal,time,net,ipc,...}.rs
→ task / mm / fs / net 领域对象
→ os/src/mm/mod.rs::copy_to_user
→ trap context 写回返回值或 errno
```

参数读取失败不能留下部分状态；copyout 失败前后是否允许提交状态，要按对应 Linux ABI 单独判断。

### clone / exec / exit / wait

```text
sys_clone
→ TaskControlBlock 克隆资源
→ MemorySet::from_existed_user（独立地址空间时）
→ FdTable 复制或共享
→ 发布新任务到 scheduler

sys_execve
→ 复制 pathname/argv/envp
→ ELF 装载与新 MemorySet
→ 清理 sibling thread 用户地址
→ 提交新 trap context

sys_exit / sys_exit_group
→ 退出状态和资源归属
→ 唤醒 parent/waiter
→ scheduler 切走

sys_wait4
→ child 事件匹配
→ 可中断睡眠/唤醒
→ 状态与 rusage copyout
→ 成功后回收
```

主要入口在 `os/src/syscall/process.rs`、`os/src/task/task.rs`、`os/src/task/scheduler.rs` 和
`os/src/mm/memory_set.rs`。并发 bug 要明确哪个动作是提交点，不能用 `Arc::strong_count` 猜资源归属。

### 缺页

```text
arch trap handler
→ 解析 fault cause + fault address + user SP
→ MemorySet::handle_page_fault
→ 查 VMA 与权限
→ lazy / COW / file-backed / grow-down 分支
→ 页表映射与 TLB 处理
→ 成功重试，或递送 SIGSEGV/SIGBUS
```

RV 入口为 `os/src/arch/rv64/trap/mod.rs::trap_handler`，LA 入口为
`os/src/arch/loongarch64/trap/mod.rs::trap_handler`，公共处理在
`os/src/mm/memory_set.rs::handle_page_fault`。记录 fault address、PC、SP、访问类型、VMA 区间、权限、
backing 和文件当前 EOF。ELF `PT_LOAD` 尾页与普通动态文件 mmap 的 EOF 规则不能混用。

### 文件 I/O 与 mmap

```text
read/write/openat/mmap syscall
→ FdTable
→ File（open file description：offset/flags/error cursor）
→ FileOp / namei / dentry / inode
→ 普通文件 PageCache
→ ext4 lower operation / block device
```

普通文件 buffered I/O 与 `MAP_SHARED` 应共享同一 PageCache 页帧。排查“写后读旧值”时依次确认
inode identity、缓存 identity、dirty owner、truncate/hole punch、writeback error 和锁外 I/O；不要
额外建立第二份 mmap 缓存。

### 调度、阻塞与唤醒

```text
阻塞 syscall
→ 登记等待条件/事件源
→ block 当前任务
→ processor::run_tasks / scheduler::fetch_task
→ 事件、timer、signal 或 peer close
→ scheduler::wakeup_task
→ 重新检查条件后继续
```

“CPU 还在跑但程序不前进”常是丢唤醒或轮询。检查登记等待是否早于事件发布、唤醒对象是否准确、
条件是否在锁内复检、signal restart 是否正确、timer deadline 是否被 100 Hz tick 粗化。pipe、futex、
wait、socket 不应靠 `yield` 忙轮询代替事件源。

## 关键对象与所有权

| 对象 | 位置 | 排查时要问 |
| --- | --- | --- |
| `TaskControlBlock` / `ThreadGroup` | `os/src/task/task.rs` | 谁拥有线程组资源，退出的唯一提交者是谁？ |
| `Scheduler` | `os/src/task/scheduler.rs` | 任务当前在哪个状态/队列，谁能唤醒？ |
| `MemorySet` / VMA | `os/src/mm/memory_set.rs` | 映射是 private/shared、anonymous/file、lazy/COW 中哪一种？ |
| 用户拷贝边界 | `os/src/mm/mod.rs` | 地址检查、跨页 fault、部分拷贝和 errno 是否正确？ |
| `FdTable` | `os/src/fs/fdtable.rs` | fd 表是复制还是共享；fd 是否仍指向同一个 File？ |
| `File` / `FileOp` | `os/src/fs/file.rs` | offset/flags 属于 open file description 还是 inode？ |
| `PageCache` | `os/src/fs/page_cache.rs` | 页帧、dirty、writeback error 与 inode identity 是否唯一？ |
| `Pipe` | `os/src/fs/pipe.rs` | reader/writer 数、EOF/EPIPE、PIPE_BUF 原子性和唤醒是否一致？ |

## 四类现场故障树

### 无法启动

1. `file kernel-*` 和 `rust-readobj -h -l kernel-*` 检查产物格式、entry 与 segment。
2. 对照构建平台与 QEMU/真机平台，确认没有把 raw binary 当 ELF 或反过来。
3. 查 `main.rs` 初始化最后成功阶段，再查平台串口、内存区间、根块设备与 SMP 放行。
4. 单核能启动、多核失败：重点查 secondary 启动顺序、timer service、IPI/TLB 和共享初始化。

### SIGSEGV / SIGBUS

1. 保存 PC、fault address、SP、访问类型、signal 和 errno。
2. 判断地址是否落在 VMA，访问是否符合 VMA 权限。
3. 确认 PTE、COW、lazy allocation、文件 EOF 和 PageCache backing。
4. 只在 LA 失败时查 PTE 高位、TLB invalidate、非对齐访问；只在 RV 失败时查 early/direct map 范围。

### 卡死或超时

1. 区分 guest 真卡死、测试仍运行、QEMU 慢、host 调度不足和测试框架等待。
2. 看最后一次阻塞 syscall，以及等待条件、waiter 注册和对应 wakeup。
3. 查 signal pending/mask、SA_RESTART、timer deadline、futex key、pipe/socket peer close。
4. 不以 `make` 或 QEMU 的退出码代替 guest 日志结论。

### 文件系统异常

1. 区分 pathname、fd、open file description、inode、PageCache 与 lower ext4 层。
2. 检查权限和 errno 的优先顺序，失败是否原子。
3. 查 inode/dentry 缓存 identity 与 generation，确认 unlink 后的活引用语义。
4. 查 dirty/writeback、ENOSPC/EIO、truncate、hole、`st_blocks` 和时间戳提交。
5. 先用只读 `debugfs -R` 检查镜像；不要为查看文件而修改官方镜像。
