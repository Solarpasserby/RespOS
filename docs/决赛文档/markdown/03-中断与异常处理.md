# 3. 中断与异常处理

> 本章回答：用户态或内核态发生 trap 后，RespOS 如何保存现场、识别原因、调用相应内核服务，并在保证现场完整的前提下返回？

## 3.1 模块定位

中断与异常处理是用户程序进入内核的统一入口，也是时钟、系统调用、缺页和进程抢占等机制的连接点。RespOS 将处理过程分为两层：架构相关的入口与返回代码负责完成寄存器保存、特权级切换和硬件状态恢复；架构无关的 Rust 代码负责识别 trap 原因，并调用系统调用、内存管理、信号和调度模块。

这种划分使得两种架构可以共享同一套处理策略，同时保留各自必要的硬件细节。图 3-1 展示了一次用户态 trap 的完整路径。

```text
用户程序
   │  ecall / 缺页 / 定时器中断
   ▼
架构入口汇编：切换栈、保存寄存器与状态
   ▼
Rust trap_handler：读取原因并分发
   ├─ 系统调用 → syscall → 写回返回值
   ├─ 缺页异常 → MemorySet::handle_page_fault
   ├─ 定时器中断 → 重设时钟、检查计时器、触发抢占
   ├─ 非法指令/断点 → 退出或处理调试事件
   └─ 软件中断 → 响应核间通知
   ▼
信号处理与调度检查
   ▼
架构返回汇编：恢复现场、恢复用户态入口、sret/ertn
```

图 3-1  用户态 trap 的入口、分发与返回路径

图中的“入口汇编”和“Rust 分发”并不是两条独立的异常路径：前者提供一个可靠的运行现场，后者在这个现场上修改下一次恢复时应使用的寄存器和 PC。最终返回的其实是修改后的 `TrapContext`。

## 3.2 Trap 的基本流程

### 3.2.1 入口：从硬件状态到可操作现场

trap 可以分为同步异常和异步中断。系统调用、非法指令、断点和缺页异常由当前指令直接引起；定时器中断和软件中断则可以在指令流之外到达。硬件首先把返回地址和原因写入架构寄存器，再跳转到预先配置的入口地址：RISC-V 使用 `sepc`、`scause`、`stval` 等寄存器，LoongArch 使用 `ERA`、`ESTAT`、`BADV` 等寄存器。

入口汇编随后完成三件事：选择内核栈，保存通用寄存器和返回所需的状态寄存器，将当前 trap vector 切换为内核入口，最后调用 Rust 处理函数。保存后的现场位于内核栈上，而不是用户地址空间中；这保证了内核可以在用户页表或用户栈不可靠时仍然读取和修改现场。

### 3.2.2 分发：同一入口承载多种内核服务

Rust 处理函数直接读取硬件原因寄存器，再根据来源和原因进行分发。`TrapContext` 只保存“返回时需要恢复的执行状态”，并不重复保存 `scause`、`stval`、`ESTAT` 或 `BADV`；这些信息在分发阶段从 CSR 读取。

用户态与内核态使用不同的错误策略。用户态的非法访问通常转化为信号或进程退出，使单个应用失败不会破坏内核；内核态发生非法指令、缺页或系统调用则被视为内核不变量被破坏，处理函数会报告错误并 panic。定时器中断在两种模式下都需要重设下一次触发时间，但只有满足安全条件时才执行计时器检查或调度动作。

### 3.2.3 返回：把“下一条要执行什么”交还给硬件

分发函数可以修改保存的 PC、通用寄存器和状态。例如系统调用需要跳过 `ecall` 指令并把返回值写入 ABI 规定的返回寄存器；信号处理和 `sigreturn` 也通过修改现场完成用户态控制流切换。处理完成后，入口汇编恢复寄存器，恢复用户态 trap vector，并执行 RISC-V 的 `sret` 或 LoongArch 的 `ertn`。

## 3.3 TrapContext：统一的可恢复现场

`TrapContext` 是汇编布局与 Rust 代码之间的契约，使用 `#[repr(C)]` 保证字段布局稳定。两种架构的具体字段有所不同，但都围绕“保存寄存器、返回 PC 和特权状态”这一目标组织。

| 架构 | 现场内容 | 返回状态 | 关键 ABI 寄存器 |
| --- | --- | --- | --- |
| RISC-V 64 | `x[32]`、浮点寄存器 `f[32]`、`fcsr` | `sstatus`、`sepc` | `a0` 为返回值，`a7` 为系统调用号 |
| LoongArch 64 | `x[32]` | `prmd`、`era` | `a0` 为返回值，`a7` 为系统调用号 |

表 3-1  两种架构 TrapContext 的主要内容

RISC-V 需要同时保存浮点现场，因为用户态浮点寄存器也属于被保护的执行状态；LoongArch 的当前上下文结构则按本架构入口汇编保存通用寄存器和 `PRMD/ERA`。用户栈指针也保存在通用寄存器数组中：RISC-V 为 `x[2]`，LoongArch 为 `x[3]`。因此它不是额外的 `user_sp` 字段。

系统调用分发体现了这份契约的实际用途：处理函数从 `a7` 和参数寄存器读取调用信息，推进返回 PC，调用公共系统调用入口，再把结果写回 `a0`。图 3-2 总结了现场的生命周期。

```text
硬件写入返回 PC/原因
        │
        ▼
入口汇编保存 TrapContext 到内核栈
        │
        ▼
Rust 读取原因并修改 TrapContext
        │       ├─ 返回值写入 a0
        │       ├─ sepc/era 跳过 ecall
        │       └─ 信号/调度改变待恢复上下文
        ▼
返回汇编按固定布局恢复
        │
        ▼
       sret / ertn
```

## 3.4 主要 trap 类型与内核协作

### 3.4.1 系统调用

系统调用是最明确的同步入口。用户程序执行 `ecall` 后，内核根据架构 ABI 取出系统调用号和参数，推进 `sepc` 或 `ERA`，再调用公共 `syscall` 分发器。返回结果写回 `a0`，随后由统一返回路径恢复用户程序。

推进 PC 是必要的：如果不跳过触发 trap 的 `ecall`，返回后会再次执行同一条指令，形成无限陷入。系统调用本身的权限检查和对象操作由各子系统完成，trap 模块只负责建立调用边界和交付参数。

### 3.4.2 缺页异常

缺页处理首先根据异常原因区分取指、读访问和写访问，再从 `stval` 或 `BADV` 取得出错虚拟地址，交给当前任务的 `MemorySet`。内存管理模块可以据此完成按需映射、权限检查或写时复制等操作。

处理成功时，返回 PC 保持不变，用户重新执行引发缺页的指令；处理失败时，内核将错误转换为相应信号，通常把设备 I/O 错误映射为 `SIGBUS`，其他不可恢复的地址访问映射为 `SIGSEGV`。这样，异常恢复策略与地址空间实现解耦。

### 3.4.3 定时器、软件中断与抢占

定时器处理遵循“先确认、再重设、后处理”的顺序：清除或确认当前中断状态，设置下一次触发时间，检查到期的内核计时器，并在需要时触发当前任务抢占。时钟模块中的 nanosleep、POSIX timer 和 timerfd 都通过这条硬件时钟路径获得推进。

软件中断主要承担核间通知功能。处理函数确认通知后清除对应状态，避免同一通知重复触发。定时器和软件中断都可能在内核态到达，因此内核 trap handler 只在安全的空闲点执行任务计时器检查，避免在持有关键内核状态时直接切换上下文。

### 3.4.4 非法指令、断点与信号

非法指令和断点属于同步异常。用户态非法指令会导致当前任务退出，断点则按调试语义结束或交给相应处理；内核态对应异常则被视为严重错误。各类用户态 trap 完成主要处理后还会统一调用信号处理逻辑，因此缺页、定时器和系统调用产生的待处理信号可以在同一返回边界交付给用户程序。

## 3.5 中断屏蔽与并发安全

trap 处理不仅要识别事件，还要避免处理过程被同类事件破坏。RespOS 为两种架构提供统一语义的 `InterruptGuard`：构造时保存当前中断使能状态并关闭中断，离开作用域时仅在原先开启的情况下恢复。这样既能保护临界区，也不会无条件打开调用者原本关闭的中断。

| 场景 | RISC-V 机制 | LoongArch 机制 | 共同语义 |
| --- | --- | --- | --- |
| trap 入口 | 配置 `stvec`，进入内核入口 | 配置 `EENTRY`，进入内核入口 | 先建立内核可用的保存环境 |
| 中断总开关 | `sstatus.SIE` | `CRMD.IE` | 由 guard 保存并按原状态恢复 |
| 用户态返回 | `sret` 根据 `sstatus` 返回 | `ertn` 根据 `PRMD/ERA` 返回 | 只在现场完整后恢复用户态 |
| 定时器状态 | SBI 设置下一次触发 | 清除定时器状态并配置下一次触发 | 重新武装后再执行计时器服务 |

表 3-2  双架构 trap 控制语义对照

RISC-V 返回路径尤其强调顺序约束：恢复寄存器的中间阶段先保持 `SIE` 关闭，待通用寄存器和浮点寄存器全部恢复后，才切回用户态 trap vector。否则定时器可能在现场尚未恢复完成时再次进入 trap，导致使用半恢复状态的寄存器。LoongArch 则在 `ertn` 前准备好 `PRMD`、`ERA`、用户态入口和栈切换信息，再由硬件完成特权级返回。

设备外部中断的具体控制由架构和驱动层共同承担：架构层负责把硬件中断送入统一 trap 路径，驱动层负责识别设备、清除设备状态并完成请求。这样可以把“如何进入内核”和“哪个设备需要服务”分开，避免 trap 分发器依赖具体设备实现。

## 3.6 功能与设计总结

| 设计点 | 实现方式 | 对系统的作用 |
| --- | --- | --- |
| 统一入口 | 架构汇编保存现场，Rust 统一分发 | 系统调用、异常和中断共享清晰的边界 |
| 可修改现场 | `TrapContext` 作为返回上下文 | 返回值、信号、抢占都可通过同一机制生效 |
| 用户/内核分流 | 用户错误转信号或退出，内核错误 panic | 隔离应用故障，尽早暴露内核不变量破坏 |
| 架构复用 | 共享处理策略，保留各自 CSR 与返回指令 | 支持 RISC-V 与 LoongArch 的一致功能语义 |
| 返回安全 | 固定保存布局、屏蔽顺序和栈切换协议 | 避免重入、现场损坏和错误特权级返回 |

中断与异常模块因此承担的是一条完整的控制流闭环：它把硬件事件转换为内核服务，把服务结果写回可恢复现场，再将控制权安全地交还给任务。内存、时钟、进程、信号和驱动模块则分别在这条闭环的分发节点上实现各自功能。
