# 13. AI 工具使用说明

> 本章是披露骨架，不预设团队实际使用过哪些工具。必须由团队根据真实记录填写，不能用模型推测补齐。

## 14.1 工具与使用场景清单

【本节目的】完整列出使用过的 AI 工具、账号/版本范围和时间段。

【建议写什么】填写工具名称、版本/模型、使用日期、成员、场景（代码阅读、方案讨论、Debug、测试分析、文档）、输入/输出类型。

【建议检查的 RespOS 代码】Git commit、PR/issue、开发记录、终端记录和团队 AI 使用日志；只看与项目有关的记录。

【建议查看的 Git 历史】按真实记录绑定 commit；无法证明的内容写“待人工确认”。

【建议准备的图 / 表】工具—场景—输出—人工责任表。

【建议准备的测试 / 数据】若 AI 建议影响代码，列建议前后 commit、测试命令和人工复核结果。

【容易出现的问题】不能把所有代码归因于 AI；也不能隐瞒 AI 参与的测试、Debug 或文档整理。

## 14.2 AI 产生内容与人工复核

【本节目的】说明 AI 的建议如何被验证、修改或拒绝。

【建议写什么】按案例填写 AI 输出摘要、实际采用部分、人工修改、源码/测试证据、未采用原因和责任人。

【建议检查的 RespOS 代码】对应 commit diff、测试日志、review 记录；不复制会话原文或隐私数据。

【建议查看的 Git 历史】关联 `git show` 和测试提交；区分 AI 建议日期与代码合入日期。

【建议准备的图 / 表】建议→人工审查→代码变更→测试结果流程；采用/拒绝分类表。

【建议准备的测试 / 数据】双架构 build、专项 probe、关键 runtime；AI 不能作为测试证据本身。

【容易出现的问题】“AI 生成并通过”不说明语义正确；需说明谁验证了生命周期、锁和失败路径。

## 14.3 合规与数据边界

【本节目的】说明输入 AI 的内容、第三方代码、凭据和个人数据如何处理。

【建议写什么】填写是否上传源码片段、是否脱敏、是否使用私有资料、输出许可证审查和人工最终责任。

【建议检查的 RespOS 代码】`.gitignore`、公开/私有配置、团队记录和第三方清单；不得把 token/会话导入文档。

【建议查看的 Git 历史】只引用公开可审计的项目事实；AI 记忆不作为版本证据。

【建议准备的图 / 表】数据类别—处理方式—责任人—保留期限表。

【建议准备的测试 / 数据】许可证/来源审查结果；若无记录，明确写“待人工确认”。

【容易出现的问题】本章不应包含凭据、原始聊天记录、个人数据或无法验证的工具宣传语。
