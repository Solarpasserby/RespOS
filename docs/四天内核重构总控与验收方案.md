# RespOS 四天内核重构总控与验收方案

> 适用范围：三名开发者、四天集中重构  
> 核心原则：正确性优先，性能必须测量，重构必须可回退  
> 本文负责整体排期、合并、审查和验收。个人任务见：
>
> - [A：进程、同步、调度与时钟](./四天内核重构-A-进程同步时钟.md)
> - [B：内存管理](./四天内核重构-B-内存管理.md)
> - [C：文件系统与文件 ABI](./四天内核重构-C-文件系统.md)

## 1. 本轮目标

本轮不是全面重写 RespOS，也不以增加 syscall 数量为目标。四天结束时，希望达到：

1. 核心路径中的 panic、假成功、明显资源错误释放得到处理；
2. 进程、内存和文件系统的关键状态变化具有明确不变量；
3. futex、阻塞、时钟等跨模块语义的支持边界更清楚；
4. 修改过的代码职责更集中，重复状态机和重复校验减少；
5. 选定性能热点有修改前后的数据；
6. 建立一组比完整 LTP 更快、更容易定位问题的小回归；
7. 所有重要修改可以按语义单独回退。

成功不意味着完整兼容 Linux，而意味着：

```text
核心能力可信
+ 简化能力诚实
+ 错误可以稳定复现
+ 修改可以安全回退
```

## 2. 非目标

四天内明确不做：

- 完整 Linux ABI；
- CFS；
- 完整实时调度；
- PI futex；
- 完整 capability、ACL、namespace；
- NUMA、swap、完整页面回收；
- 后台 writeback 和崩溃一致性；
- VFS、页表或 TaskControlBlock 的整体重写；
- 网络模块重构；
- 真正 SMP 并发支持；
- 大规模目录调整和全局重命名。

这些内容即使重要，也不能在四天内同时满足正确性、双架构和比赛稳定性。

## 4. 开发环境和分支

建议每人使用独立 worktree，特别是在高度依赖 Codex 时，避免多个会话共享工作区造成覆盖。

示例：

```bash

git worktree add ../RespOS-mm -b refactor/mm-contract
git worktree add ../RespOS-fs -b refactor/fs-consistency
```

现有未提交文件属于原作者，不应因为重构而删除、覆盖或混入无关提交。

每个分支要求：

- 从同一 baseline 创建；
- 每个提交只处理一个语义；
- 提交信息说明“修复了什么状态错误”；
- 不提交构建产物、镜像和运行日志；
- 不在功能提交中混入全文件格式化。

## 5. 统一优先级

| 等级 | 定义 | 示例 |
| --- | --- | --- |
| P0 | panic、内存破坏、数据丢失、死锁、错误释放 | 共享 mm 被提前回收、sync `todo!()` |
| P1 | 假成功、丢失唤醒、生命周期错误 | CPU clock 冒充墙上时间、重复 wake |
| P2 | errno、flags、边界和代码耦合 | flags 被静默忽略、地址溢出 |
| P3 | 有基准证明的性能问题 | 锁内 I/O、重复堆分配 |
| P4 | 纯美化和目录调整 | 重命名、拆大文件 |

执行顺序固定为：

```text
P0 → P1 → P2 → P3 → P4
```

第四天下午只能继续 P0/P1 和回归修复。

## 6. ABI 治理规则

### 6.1 四级分类

| 等级 | 含义 | 要求 |
| --- | --- | --- |
| A | 核心语义已实现且有回归 | 保持支持 |
| B | 只支持明确子集 | 校验 flags/对象，超出范围返回错误 |
| C | 明确不支持 | 返回合适的 `ENOSYS`/`EOPNOTSUPP` |
| D | 假实现 | 本轮优先修正或降级为 C |

删除复杂实现通常不意味着删除 syscall number。明确拒绝一般比返回成功但不产生效果更安全。

### 6.2 ABI 台账模板

每个负责人只整理自己本轮触及的接口：

| syscall | 等级 | 支持范围 | 状态变化 | 关键 errno | 并发语义 | 回归测试 |
| --- | --- | --- | --- | --- | --- | --- |
| 示例：preadv | A | flags=0 | 不修改共享 offset | EBADF/EFAULT/EINVAL | positioned read | `preadv_offset` |

### 6.3 统一规则

- syscall 层只负责 copyin、参数校验、调用核心对象和 copyout；
- 不支持的 flags 不能静默忽略；
- 用户输入不能触发内核 panic；
- 返回成功必须产生接口承诺的状态变化；
- 测例名、程序名、路径前缀不能决定 syscall 行为；
- ABI struct 必须使用明确布局；
- 长度乘法、地址加法和页对齐必须检查溢出；
- copyout 失败前不能提交不可逆状态，或者必须有明确回滚。

### 6.4 syscall 风险评分

216 个 syscall 不能平均投入审查时间。每个负责人先按下面规则评分，优先深审总分不低于 5 的接口：

| 风险因素 | 分值 |
| --- | ---: |
| 修改全局或跨进程共享对象 | +3 |
| 创建、销毁 fd 或内核对象 | +2 |
| 会阻塞、唤醒、超时或发送 signal | +2 |
| 修改状态后还需要 copyout | +2 |
| 受 fork、exec、dup、close 或 exit 影响 | +2 |
| 涉及凭据、权限或安全承诺 | +2 |
| 纯只读且无副作用的查询 | -2 |

高风险家族优先顺序：

```text
clone/exec/exit/wait
→ futex/epoll/poll/timer
→ mmap/mremap/mprotect/shmat
→ open/rename/unlink/mount
→ credentials/rlimit/scheduler
→ read/write/splice/socket
→ 纯查询
```

高风险 syscall 必须填写：

```text

输入指针、长度、flags、fd/id：

所有 copyout：
第一次状态修改：
最终提交点：

回滚方式：

持有的锁：
阻塞条件：
唤醒来源：
signal 行为：
timeout 使用的时钟：

fork：
exec：
dup：
close：
exit：
pid/fd/id 复用：

Linux 参考：
最小回归：

```

没有填清“共享边界、提交点、失败状态、退出清理”的接口，不能评为 A。

### 6.6 对象型 syscall 的完整生命周期

返回 fd、timer id、shmid 或其他 handle 的 syscall 不能只测试创建：

```text
create
→ use/read/write/ioctl/mmap/poll
→ dup/fork
→ exec/CLOEXEC
→ close/delete
→ owner exit
→ last reference release
→ number reuse
```

只返回一个整数、后续没有真实对象语义的接口属于 D 级能力误报，应降级为 C。

第一天重点核查当前通过通用空 `SpecialFd` 暴露的接口：

- `inotify_init1`
- `signalfd4`
- `pidfd_open`
- `fanotify_init`
- `userfaultfd`
- `perf_event_open`
- `io_uring_setup`
- `bpf`
- `fsopen`
- `fspick`
- `open_tree`
- `memfd_secret`

默认处理是返回 `ENOSYS`。只有完成最小生命周期并有测试的接口才保留。

### 6.7 prepare/commit 结构

状态型 syscall 优先整理为：

```text
copyin 全部输入
→ 校验 flags、范围、权限和对象类型
→ 获取稳定对象引用
→ prepare，不修改共享状态
→ 能提前输出的旧状态先 copyout
→ commit
→ 必要时通知 waiter
```

若 commit 后必须 copyout，则必须明确 Linux 的失败语义，并提供回滚或测试固定其行为。单纯提前检查用户地址不能替代回滚，因为共享地址空间中的其他线程可能并发 unmap。

第一天重点查找：

- 插入全局表后才 copyout；
- 回收对象前才 copyout；
- 更新限制、timer、credential 后才 copyout；
- 消费 edge/oneshot event 后才 copyout；
- 分配 attach id 后才完成地址/flags 校验。

### 6.8 失败注入矩阵

每个状态型接口至少选择相关场景：

- 每个用户指针分别传入非法地址；
- 输出结构跨页且第二页非法；
- 未知 flags bit；
- 长度和地址溢出；
- 错误 fd/id 和错误对象类型；
- fd、frame、id 等资源耗尽；
- 重复 create/delete/close；
- owner 在对象存活期间 exit；
- fd/pid/id 被复用；
- wake、timeout、signal 相邻发生；
- fork/exec 前后观察状态。

失败后必须检查内核状态，而不仅检查 errno。

### 6.9 当前代码的首批红名单

本轮已知需要优先确认：

1. 空 `SpecialFd` 冒充完整子系统；
2. POSIX timer 在 copyout timer id 前进入全局表；
3. POSIX timer 缺少进程退出清理，且只以数字 tgid 标识 owner；
4. `timer_settime`、`prlimit64` 等接口的状态修改/copyout 顺序；
5. `shmat` 在完成地址校验前修改 attach 表和时间；
6. `epoll_pwait` 忽略 signal mask 和 sigset size；
7. epoll edge/oneshot 状态可能在 events copyout 失败前被消费；
8. CPU clock、TAI、alarm clock 使用同一墙上/启动时间冒充；
9. `clock_getres` 报告与实际不符的分辨率；
10. `madvise` 对状态型 advice 返回假成功；
11. `mlock` 未做进程累计 locked bytes 记账；
12. `get_mempolicy` 的输出规模和单节点受限语义；
13. `SCHED_FIFO` 与 `SCHED_RR` 实际行为没有清晰区分；
14. `getrandom` 不是密码学安全随机源；
15. ABI 路径中的可达 `unwrap/expect`，例如 parent Weak 失效。

首批红名单只要求做出“修复、受限支持、明确拒绝”三种结论，不要求全部补成完整 Linux。

### 6.10 ABI 合入门槛

以后任何 syscall 从 `ENOSYS` 变为支持，或从 C/B 提升等级，必须同时提交：

1. 状态影响审计表；
2. 精确支持范围；
3. flags、errno 和非法指针测试；
4. 至少一个失败后状态不污染测试；
5. 相关 fork/exec/dup/close/exit 生命周期说明；
6. RV 与 LA 测试；
7. 未实现部分的明确错误；
8. 不依赖测试程序名、路径或空壳对象。

## 7. 统一不变量

### 7.1 任务

- tid 不能同时 ready 和 blocked；
- exit 与 wait 分离；
- wake、timeout、signal 只能有一个完成原因；
- 退出任务不残留在调度、futex、timer 和资源等待队列；
- parent/children 双向关系一致。

### 7.2 内存

- VMA 使用半开区间；
- VMA 有序、不重叠；
- VMA、PTE 和 Frame 生命周期一致；
- COW 页权限明确；
- 用户地址访问必须经过范围和权限检查；
- 失败不能留下半提交映射。

### 7.3 文件系统

- fd entry 与打开文件对象职责分离；
- positioned I/O 不修改共享 offset；
- dentry、inode、path 和 mount 身份明确；
- rename/unlink 不破坏已打开 fd；
- writeback 失败不能错误清 dirty；
- 慢 I/O 不长期持有不可睡眠全局锁。

## 9.4 第四天：交叉审查、性能和冻结

### 上午：交叉审查

| 审查者 | 被审查范围 | 重点 |
| --- | --- | --- |
| A | C 的 fd/pipe/page cache | 生命周期、阻塞和唤醒 |
| B | A 的 exit/futex | 用户地址、共享 mm、copyout |
| C | B 的 file mmap | backing、writeback、锁顺序 |

每人只深入一条跨模块调用链，必须回答：

1. 状态在哪里修改？
2. 失败是否留下半提交状态？
3. 是否持有 spin lock 做 copyin/copyout、调度或 I/O？
4. 对象由谁持有，何时释放？
5. wake/timeout/signal 是否可能重复完成？
6. RV 和 LA 是否使用同一份公共语义？

### 中午：性能对比

至少比较：

- syscall/getpid latency；
- context switch 或 yield；
- pthread/futex；
- fork+COW；
- 4 KiB/64 KiB/1 MiB 文件读写；
- page cache hit；
- 测试前后 free frame。

每项至少运行 5 次，比较中位数。

性能判断：

- 核心指标稳定退化超过 5% 时必须解释或回退；
- 正确性修复造成的小幅退化可以保留，但要记录；
- 没有测量改善的微优化不作为本轮成果；
- debug invariant 不应进入 release 热路径。

### 下午：冻结

允许：

- P0/P1 修复；
- 编译修复；
- 确定性测试修复；
- helper 收敛；
- 注释与 TODO 分类；
- 删除确认死代码。

禁止：

- 新 syscall；
- 新调度算法；
- 新锁框架；
- VFS/MemorySet/TaskControlBlock 重写；
- 大规模拆文件；
- 网络改造；
- SMP；
- 为提高分数加入测试特判。

## 11. 测试体系

### 11.1 第一层：宿主机模型

适合：

- VMA 切分；
- fd/open-file 共享；
- exit/wait；
- ready/blocked；
- wait completion。

模型只保留核心不变量，不模拟硬件。

### 11.2 第二层：小型用户态回归

每个回归只验证一个语义，输出：

```text
操作
返回值
errno
关键状态
PASS/FAIL
```

同一个程序尽量能在 Linux 和 RespOS 上运行，比较外部行为而不是内部实现。

### 11.3 第三层：现有测试套件

顺序：

```text
单个回归
→ 模块 smoke
→ 相关 LTP 子集
→ 固定综合集合
→ 完整 LTP/比赛流程
```

完整 LTP 失败时先确认：

- 测试本体失败；
- harness 初始化失败；
- 文件系统临时目录失败；
- timeout；
- 环境能力探测差异。

## 12. 锁与阻塞审查

三组共同维护一张锁依赖表。

最低规则：

- spin lock 内禁止调度和阻塞；
- spin lock 内避免磁盘 I/O；
- copyin/copyout 不应在全局锁内执行；
- 同级对象锁需要稳定顺序；
- 慢操作尽量采用 prepare/execute/commit；
- waiter 登记和 blocked 状态之间不能丢失唤醒；
- 唤醒时先确定唯一完成者，再做调度器迁移。

锁表模板：

| 锁 | 保护状态 | 可否在中断中获取 | 锁内可否 copy | 锁内可否 I/O | 允许嵌套 |
| --- | --- | --- | --- | --- | --- |
| SCHEDULER | ready/blocked | 视实现 | 否 | 否 | 待填写 |

## 13. 性能工作原则

“代码更短”不等于更快，“锁更细”也不一定更正确。

只处理能够观察的热点：

1. 锁内磁盘 I/O；
2. syscall read/write 反复分配；
3. 重复用户页翻译；
4. page cache hit 仍访问后端；
5. 调度器重复全表扫描；
6. release 路径中的调试检查。

性能修改必须记录：

```text
测试环境
输入规模
修改前 5 次
修改后 5 次
中位数
正确性回归
```

不允许通过以下方式优化：

- 绕过用户权限检查；
- 假 fsync；
- 删除必要 TLB flush；
- 扩大全局锁掩盖并发问题；
- 缓存失效的裸指针；
- 针对测试程序名走特殊路径。

## 14. 代码清晰度验收

本轮不以物理拆文件为主，而以职责收敛为主。

修改过的路径应满足：

- syscall 层保持薄；
- 同一 flags 校验集中一处；
- 同一状态机不保留多份近似实现；
- 退出资源清理有统一入口；
- VMA 范围计算有统一入口；
- positioned I/O 不模拟共享 offset；
- 注释说明原因和不变量；
- 临时逻辑使用统一标记：

```text
TODO[ABI-COMPAT]
TODO[VFS-CONSISTENCY]
TODO[LOCKING]
TODO[LWEXT4]
TODO[PERFORMANCE]
```

不要求所有函数达到固定行数，也不为了“美观”引入过度抽象。

## 19. 决赛基线判定
