# 6. 进程间通信与信号

> 本章回答：信号如何发送、挂起、投递和处理？管道、futex、共享内存如何实现？

RespOS 的进程间通信不是一个孤立模块，而是由信号（异步通知）、管道（字节流）、futex（用户态同步原语）和共享内存共同组成。每个机制有不同的适用场景和设计约束。

## 6.1 信号机制

> 【本节目的】完整解释信号从发送到处理的链路。

RespOS 将 signal 状态按线程和进程两层管理。每个线程拥有自己的待处理集合（pending）、屏蔽集（mask）和备用信号栈，因此不同线程可以独立屏蔽或等待信号；同一线程组共享 handler 表，使任意线程调用 `sigaction` 后整个进程看到一致的处理规则。

signal 既可能来自 `kill/tkill/tgkill`，也可能来自用户缺页、非法访问、timer、pipe 或子进程状态变化。线程级 signal 直接进入目标 tid；进程级 signal 会在线程组中选择一个当前能够接收它的线程。若目标正在 futex、sleep 或 wait 等可中断等待中，投递路径会同时争取 `Interrupted` 状态并唤醒任务，避免 signal 已经 pending、线程却一直睡着。

完整处理流程如下：

```text
signal 产生 → 写入目标线程 pending → 必要时打断 Blocked
→ trap 返回用户态前取出一个 signal
→ 在普通栈或 alt stack 构造 signal frame
→ 跳到用户 handler → trampoline 调用 sigreturn
→ 恢复寄存器、PC 和 signal mask
```

普通 handler 的 frame 保存寄存器现场和旧 mask；设置 `SA_SIGINFO` 时还会传入 `siginfo_t` 与 `ucontext`。`SA_ONSTACK`、`SA_NODEFER`、`SA_RESETHAND` 也已接入这条路径。没有用户 handler 时，内核按默认规则执行忽略、终止、停止或继续；当前 Core 类信号只执行终止，尚不会生成 core 文件。

signal 返回曾经暴露过一个更底层的问题：保存的用户上下文可能带有不安全的中断状态，而 trap restore 又过早切换到用户 trap vector，导致 timer 在寄存器尚未恢复完成时重入。RV64 后来把"清 SIE、恢复寄存器、最后切换 user vector"的顺序固定下来——这个修正不仅保护普通 syscall 返回，也保护 signal handler 和 sigreturn 的返回路径。

当前 signal 仍有两个明确边界：`SA_RESTART` 尚未实现，被 signal 打断的 syscall 通常返回 `EINTR`；pending 使用位图并为每个信号号保存一份 `SigInfo`，同一种实时信号连续到达时仍会合并，尚不是完整的 Linux 实时信号排队模型。

## 6.2 管道

> 【本节目的】解释 pipe 的创建、读写、阻塞唤醒和 EOF 生命周期。

管道是 RespOS 中最基础的字节流 IPC 机制，常用于父子进程间的数据重定向。pipe 的核心是一个内核环形缓冲区，两边各有一个读写端点，每个端点对应一个 `FileOp` 实现——读端只实现 `read` 和 `read_ready`，写端只实现 `write` 和 `write_ready`。

```text
Pipe 结构：
  buffer: RingBuffer<u8>      ← 固定大小的环形缓冲区
  read_end: Arc<PipeEnd>      ← 持有 reader 引用计数
  write_end: Arc<PipeEnd>     ← 持有 writer 引用计数
```

**读写同步**。读空管道时，reader 进入阻塞状态并注册到 pipe 的等待队列，直到有数据写入或所有写端关闭。写满管道时，writer 同样阻塞，等待 reader 消费数据腾出空间。`read_ready()` 和 `write_ready()` 方法直接检查缓冲区状态——非空/非满时返回 true——这使得 poll/epoll 能高效监控 pipe 状态。

**EOF 判定**。pipe 的 EOF 不取决于缓冲区是否为空，而取决于是否所有写端都已关闭。每个 pipe 端点持有对应侧的引用计数——写端 close 时计数减一，当写端计数降到零时，reader 的 `read` 返回 0（EOF），后续 poll 报告 `EPOLLHUP`。子进程退出不等于所有写端立即释放：fork 后父子共享写端，子进程 `exit` 走延迟 TCB 回收时写端引用可能暂时不减到零。当前通过 `unshare_fd_table_for_exec` 和 `cleanup_dead_tasks` 加速引用释放。

## 6.3 Futex

> 【本节目的】解释 futex wait/wake/requeue 的调度交互和竞态处理。

futex 的常见路径只在用户内存中完成原子操作，真正发生竞争时才进入内核。RespOS 为等待者维护 256 个哈希桶：私有 futex 使用"tgid + 用户地址"作为 key；共享文件页和 fork 继承的共享页则根据页面身份与页内偏移生成 key，让父子进程能够进入同一等待队列。

一次 futex wait 可能由 wake、timeout、signal 或任务退出结束。每个 waiter 都有明确的完成状态，状态只能从 `Pending` 成功改变一次——后到的事件只负责发现自己已经输掉竞争：

| 完成者 | waiter 结果 | 调度动作 |
| --- | --- | --- |
| `FUTEX_WAKE` | `Woken` | 从 futex 队列摘除并唤醒任务 |
| deadline | `TimedOut` | 删除队列项，返回 `ETIMEDOUT` |
| signal | `Interrupted` | 删除队列项，返回 `EINTR` |
| exit | 不再返回用户态 | 清理 queue、wait 和 deadline 三处记录 |

`FUTEX_CMP_REQUEUE` 还需要保证"比较用户值"和"移动 waiter"发生在同一临界区。RespOS 先在锁外确认用户页可读，再在 futex 队列锁内进行固定 4 字节的 no-fault 读取，避免比较期间页面分配或睡眠。当前还有两个待完善点：普通 `FUTEX_WAIT` 的最终取值仍使用通用用户拷贝；两个进程分别 `shmat` 同一 System V 段时，futex key 目前使用各自的 attach id，尚不能保证进入同一等待队列。

> 【建议检查的代码】`os/src/task/futex/{mod.rs,queue.rs,wait.rs}`

## 6.4 System V 共享内存

> 【本节目的】说明 System V shmget/shmat/shmdt 的实现。

System V 共享内存由全局 `SHM_TABLE` 管理。`shmget` 根据 key 查找或创建共享段，并为段分配物理页；`shmat` 把同一组 frame 映射进调用者地址空间；`shmdt` 只移除当前 attach；`IPC_RMID` 在仍有进程使用时先标记删除，最后一个 attach 消失后才真正释放共享段。

这条路径实现了一个关键的失败原子性保证：shmat 还没有成功建图，就可能提前修改 attach 记录和时间。当前实现先准备地址、权限、frame 和 attach id，再调用 `MemorySet::mmap_area()` 建图；映射失败会撤销 attach owner，只有成功后才更新 `atime/lpid`。这一顺序让错误地址、冲突映射和权限失败不会污染全局共享段状态。

当前能力仍然是 System V IPC 的一个子集：消息队列和 semaphore 没有实现；`SHM_HUGETLB` 明确拒绝；系统没有 swap，因此 `SHM_LOCK/SHM_UNLOCK` 目前主要记录可见状态，不能理解成完整 Linux 换页锁定机制。

> 【建议检查的代码】`os/src/syscall/ipc.rs`，`os/src/mm/memory_set.rs`
