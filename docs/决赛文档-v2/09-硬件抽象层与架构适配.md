# 9. 硬件抽象层与架构适配

> 本章回答：RISC-V64 与 LoongArch64 的差异如何被统一？HAL 的设计原则是什么？

## 9.1 概述

RespOS 在多架构支持方面采用"条件编译驱动的架构特化"设计理念。通过编译时的架构选择机制，在保持单一代码库的前提下为 RISC-V 和 LoongArch 两种架构提供完全针对性的实现路径。整个适配策略遵循"共享核心逻辑、分离架构实现"的工程原则。

设计优势体现在三个方面：代码复用性——通过条件编译在架构间共享大量公共代码；可维护性——清晰的架构分层使代码结构容易理解和维护；灵活性——在不影响整体架构的情况下快速适配新硬件平台。

> 【建议写什么】
> - 设计原则："共享核心逻辑、分离架构实现"
> - "一次设计，多重实现"的工程原则
>
> 【建议检查的代码】`os/src/arch/mod.rs`

## 9.2 双架构差异总览

两种架构在多个维度上存在根本性差异，HAL 层的任务就是将这些差异封装为统一接口：

| 维度 | RISC-V64 | LoongArch64 |
|------|----------|-------------|
| 启动引导 | OpenSBI (M 态) → bootloader → _start | U-Boot (S 态) → _start |
| 分页机制 | Sv39 三级页表，内核高半区恒等映射 | DMW 直接映射窗口 + 页表映射（兼容 Sv39 格式） |
| trap 入口 | stvec CSR → trap.S → trap_handler | EEntry CSR → trap.S → trap_handler |
| trap 返回 | sret | ertn |
| 中断控制器 | PLIC (Platform-Level Interrupt Controller) | Line-Based Interrupt（多级中断使能：ECfg → TCfg → CrMd） |
| 上下文 CSR | sstatus/sepc/stval/sscratch/scause | CrMd/ERA/BAdv/SAVE/ESTAT |
| TLB 维护 | sfence.vma 指令 | tlbsrch + tlbrd 指令 + 手动重填 |
| 定时器 | mtime/mtimecmp (SBI 接口) | TCfg/TIClr 寄存器（恒等时钟频率可通过指令获取） |
| 内存发现 | FDT (Flattened Device Tree) | 板级固定配置 |

> 【建议准备的表】RV64/LA64 差异矩阵（更细粒度的对比）

## 9.3 页表管理抽象

RISC-V 使用标准的 Sv39 三级页表，内核高半区通过固定偏移（`KERNEL_OFFSET`）将物理地址直接映射到虚拟地址——物理页帧号与虚拟地址之间的确定性偏移使得内核访问物理页帧时无需额外查询页表。

LoongArch 的地址翻译更为复杂，分两阶段判断：首先检查是否符合 DMW 直接映射窗口（通过 DMW0～3 四个 CSR 配置），命中则直接截断高位作为物理地址访问；未命中则进入分页模式，通过 PGDH/PGDL 查找 TLB，miss 则触发 TLB 重填异常。LoongArch 的 TLB 以双页形式组织（每个 VPPN 对应一对奇数页和偶数页），利用 LDDIR 和 LDPTE 指令进行硬件辅助页表遍历，但目录项需要手工检测合法性。

HAL 将两种架构的差异封装为统一的页表接口：`map/unmap/query/protect`。上层 `MemorySet` 不关心底层是 Sv39 页表还是 DMW+页表混合模式。

> 【建议检查的代码】`os/src/arch/rv64/` 和 `os/src/arch/loongarch64/` 中的页表相关代码

## 9.4 Trap 处理抽象

两种架构的 trap 处理流程在 HAL 层归一为相同的三个阶段：entry（汇编保存寄存器上下文）→ handler（Rust 公共逻辑分发）→ return（恢复寄存器并返回）。

**RISC-V 路径**：硬件将 PC 写入 sepc、原因写入 scause、相关信息写入 stval → 跳转到 stvec 指定的 trap vector → `trap.S` 保存通用寄存器到栈上的 `TrapContext` → 调用 `trap_handler()` → 返回后从 `TrapContext` 恢复寄存器 → `sret` 返回用户态。

**LoongArch 路径**：硬件将 PC 写入 ERA、原因写入 ESTAT → 跳转到 EEntry CSR 指定的地址 → `trap.S` 先交换 sp 和 SAVE CSR 以保存原始栈指针 → 保存通用寄存器 → 调用 `trap_handler()` → 恢复寄存器 → `ertn` 返回。

**关键的 SIE 顺序**。RV64 的 `__restore` 路径需要严格按"清 SIE → 恢复寄存器 → 最后切换 user vector"的顺序执行。如果提前切换到用户态 trap vector，timer 中断可能在寄存器尚未完全恢复时重入，导致递归异常。这一修正不仅保护普通 syscall 返回，也保护 signal handler 和 sigreturn 的返回路径。

## 9.5 上下文抽象

两种架构的通用寄存器数量和用途基本对齐（RV64 的 x0-x31 对应 LA64 的 r0-r31），但 CSR 寄存器差异显著。HAL 通过 `TrapContext` 结构统一管理陷入时的寄存器快照：`TrapContext` 保存所有通用寄存器、PC、trap 原因、用户栈指针等信息，架构相关的 CSR 差异被限制在汇编 entry/return 路径中。

任务切换时的 `TaskContext` 则更精简——`__switch` 只保存函数调用约定要求保留的寄存器（ra、sp、s0-s11）和页表 token。两种架构的 `switch.S` 实现共享相同的 `TaskContext` 结构体定义。

> 【建议检查的代码】`os/src/arch/*/trap/context.rs`，`os/src/arch/*/task/switch.S`

## 9.6 启动流程适配

**RISC-V 启动**：OpenSBI (M 态) → bootloader → `_start` (S 态) → 设置 stvec → 初始化 MMU → `rust_main`。启动 hart 从 OpenSBI 传入的 FDT 中读取实际 RAM 大小。

**LoongArch 启动**：U-Boot → `_start` → 设置 DMW 映射窗口 → 跳转到 0 段地址 → `rust_main`。LA 启动的关键难点在于：从 U-Boot 获得控制权时 PC 处于 DMW0/DMW1 映射的地址段，要进入 0 段必须先设置 DMW 让 0 段可用。而且必须先设置 DMW1 保存当前段、再配置 DMW0 映射 0 段——如果直接覆盖 DMW0，当前 PC 可能立即成为非法地址。跳转必然发生在映射了新段号之后。

LoongArch 启动的另一个独特问题是时钟初始化时机。LA 的恒等时钟频率通过 `cpucfg` 指令获取，该数据需存入静态数据区域（bss 段），因此时钟初始化必须在 bss 清零之后、首次使用时钟之前完成——既不能太早（bss 未清零），也不能太晚（timer 已开始使用）。
