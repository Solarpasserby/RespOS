# 内核设计文档书写方法论

> 蒸馏自 6 份优秀 OS 比赛决赛文档：NPUcore(2024)、Chronix(2025)、Del0n1x(2025)、Noaxiom(2025)、RocketOS(2025)、Undefined-OS(2025)

---

## 一、文档整体骨架：11-12 章黄金结构

六份文档的章节排列几乎完全一致，这是被反复验证的最佳叙事弧线：

| 章序 | 章节名 | 回答的核心问题 |
|------|--------|---------------|
| 1 | 概述 / 系统简介 | 这是一个什么样的内核？面向什么平台？各模块完成度如何？ |
| 2 | 进程管理 / 任务调度 | 任务如何表示、创建、调度、切换、回收？ |
| 3 | 内存管理 | 物理内存如何分配？虚拟地址空间如何管理？缺页如何处理？ |
| 4 | 文件系统 | VFS 如何抽象？支持哪些具体文件系统？缓存如何设计？ |
| 5 | 进程间通信 / 信号 | 信号如何发送、挂起、投递？管道/futex/shared mem 如何实现？ |
| 6 | 时钟模块 | 时钟中断如何管理？定时器队列如何设计？ |
| 7 | 网络模块 | 协议栈架构？socket 生命周期？TCP/UDP 如何实现？ |
| 8 | 硬件抽象层 / 架构适配 | RISC-V 与 LoongArch 差异如何统一？ |
| 9 | 设备驱动 | 设备树、中断控制器、块设备/网卡驱动 |
| 10 | 硬件平台适配 | 物理开发板启动流程、内存布局、特殊问题 |
| 11 | 总结与展望 | 贡献摘要、当前限制、未来计划 |

**关键观察**：不是每个队伍都有全部 11 章——有些将时钟并入调度、有些将信号并入进程管理。但"概述→进程→内存→文件系统→IPC→HAL→总结"这条主线六份文档无一例外地遵循。

**Why**: 这是一条"读者认知链"——先知道整体(概述)，再理解执行单元(进程)，再理解资源空间(内存)，再理解持久化(文件系统)，再理解通信(IPC/信号)，最后理解底层硬件差异(HAL)。

## 二、每章内部的模块分解：五段式模板

六份文档在单个模块章节内部，几乎都遵循同一个深度递进模式：

### 模板结构

```
X.1 概述
    - 一句话说清该模块在内核中的角色
    - 点出关键设计选择（如"采用无栈协程""统一进程线程模型"）
    - 列举本模块完成的功能清单

X.2 核心数据结构
    - 展示结构体定义（完整代码块）
    - 逐字段解释其语义和生命周期
    - 说明字段的并发访问属性（不可变/仅本任务可变/多任务共享）

X.3 核心机制 / 算法
    - 描述关键流程（调度算法、缺页处理、路径查找等）
    - 配流程图或时序图
    - 关键代码片段 + 逐行解释

X.4 特殊设计与优化
    - 与"常规做法"的差异及原因
    - 性能优化策略及效果数据
    - 边界情况处理

X.5 与其他模块的交互
    - 暴露给其他模块的接口
    - 依赖其他模块的哪些保证
```

### 真实案例：Chronix 的进程管理章（第 2 章）结构

```
2.1 概述
    → "Chronix 仿照 Linux 内核，进程线程统一用 TaskControlBlock 表示"
    → 点出设计选择：无栈协程、统一 API、细粒度锁替代大锁
    
2.2 任务控制块设计
    2.2.1 内容结构设计
        → 完整 TCB 代码块 → 字段分四类解释（不可变/任务内可变/仅本任务可写他任务可读/多任务可变）
    2.2.2 任务状态
        → 状态枚举 + 状态转换图
    2.2.3 任务间关系
        → 父子关系、线程组、进程组
        
2.3 任务调度
    → 调度器设计、队列结构、调度策略
    
2.4 中断异常管理
    → trap 处理流程、用户态/内核态切换
    
2.5 多核心管理
    → per-CPU 结构、负载均衡、IPI
```

**Why**: 这个模板从"是什么(数据结构)"→"怎么工作(算法)"→"为什么这样设计(优化/差异)"→"边界在哪(交互/限制)"，形成完整的理解闭环。

## 三、代码-知识关联的四种模式（真实案例）

### 模式 1：代码块 → 逐段解说

六份文档无一例外地使用"先贴完整代码，再逐段/逐字段解读"的模式：

```
[代码片段 X.X  结构体定义]
  1  pub struct TaskControlBlock {
  2      pub tid: TidHandle,
  3      pub leader: Option<Weak<TaskControlBlock>>,
  ...
  }

接下来是对字段的分类解读：
"Chronix 将字段分为若干类：
1. 不可变字段：这些字段自任务诞生后到任务被回收都不会改变...
2. 任务内可变，不可被其他线程访问的字段：这些字段仅在任务内可访问改变..."
```

**来源**: Chronix §2.2.1, Del0n1x §2.5, Noaxiom §3.1, RocketOS §3.3

### 模式 2：设计对比（"与传统的...不同，我们..."）

```
"与 rCore 和 xv6 采用有栈方式进行任务切换不同，Del0n1x 的无栈协程不依赖
独立栈结构，转而通过状态机管理上下文状态。"
```
**来源**: Del0n1x §2.1

```
"Linux 内核对 task 这一单位结构的实现更具启发性：它并未严格区分进程和线程...
其次 rcore 设计中使用了大锁来保护内部可变性，但是这样的设计往往降低运行效率。
这也启示着 Chronix 细分任务中的字段，以提高运行效率。"
```
**来源**: Chronix §2.2.1

### 模式 3：设计决策 → 理由陈述

```
"之所以将这些内容放到这里，是因为 LoongArch 下的恒等时钟频率是可以通过指令获取的，
如果因此我们获取后存入静态数据区域，所以需要在 bss 段被清 0 后才开始处理时钟相关中断。"
```
**来源**: NPUcore §3.2

```
"这样做可以用直接继承原版 NPUcore 的部分内存布局，无需为了利用 LA 的直接映射窗口
就大量修改代码...减少代码出错空间。而且，这样可以利用直接映射减小恒等映射的开销，
在上下文无需存储页表地址，可以直接切换地址空间。"
```
**来源**: NPUcore §3.1.1

### 模式 4：问题 → 根因 → 方案 → 可选方案的展开

```
"通过对 openat 测试用例进行调试，我们最终发现问题出在操作系统对文件描述符的分配上。
Unix 标准要求...而 NPUcore 回收进程关闭的文件描述符时...
我们选择了在回收文件描述符后进行一次排序来解决这个问题。
这个方案不一定是性能最佳的方案，我们还有以下方案可选：
1. 回收时不进行排序，重新分配时使用 O(n) 时间寻找...
2. 使用二叉平衡树替换线性表...
未来此处成为性能瓶颈时，根据性能测试结果选用最优方案会是更好的选择。"
```
**来源**: NPUcore §4.1

## 四、内核开发者视角：六种高频表达句式

### 4.1 设计选择宣告：采用了...设计

> "Del0n1x 操作系统采用无栈协程作为核心任务管理模型"
> "Chronix 仿照 Linux 内核，进程线程统一用 TaskControlBlock 表示"
> "RocketOS 在多架构支持方面采用了'条件编译驱动的架构特化'设计理念"

### 4.2 比较引出差分价值：相比于/与...不同

> "与传统的每次任务切换需要保存完整栈帧及 14 个寄存器不同，Del0n1x 的无栈协程..."
> "与 FAT32 文件系统相比，EXT4 文件系统不仅允许了更大的文件大小..."

### 4.3 因果关系链：之所以...是因为...

> "之所以将时钟初始化延后，是因为 LoongArch 的恒等时钟频率需要通过指令获取，而该数据需存入静态区，因此需在 bss 清零之后处理。"
> "之所以没有直接把 CSRs 写入 DMW0，是因为如果当前 PC 处于 DMW0 区段，覆盖后将导致地址非法。"

### 4.4 关键注意点：需要特别注意的是/关键在于

> "需要注意的是，这段代码有 2 个需要注意的细节：(1)...(2)..."
> "这里的关键在于：parent blocked 的登记必须先于 child ready 的发布。"

### 4.5 优势递进：不仅...而且/更/同时

> "Titanix 的懒分配包括三个方面：（1）用户栈的懒分配...（2）用户堆的懒分配...（3）mmap 内存段的懒读取..."
> "这种设计不仅保证了代码的安全性，同时最大化提升了性能。"

### 4.6 边界诚实声明

> "目前初赛的所有测试用例已经满分通过，并截至到 7 月 29 日，我们是决赛 LA 赛道唯一得分队伍。"
> "目前 NPUcore-IMPACT 已经完美支持了 fat32 文件系统，但因耦合度较高..."

## 五、项目主导者视角：三个必填段落

六份文档在概述章中都有以下三段，这是"主导者"区别于"实现者"的关键：

### 5.1 分工与贡献

```
• 肖嘉誉（队长）：主要负责文件系统、信号机制、项目的构建。具体完成的贡献有：...
• 欧阳天麟：主要负责进程调度、网络、时钟管理。具体完成的贡献：...
• 周立诚：实现 slab 分配器；实现硬件抽象层...
```
**来源**: Chronix §1.3

### 5.2 参考与改进

```
• RCore：我们的项目选择 rcore ch6 的 OS 作为起点，但目前代码相较于原本的代码，
  已经经过了完全的重构。
• Phoenix：参考了其 VFS 对象的设计。对其结构体做了简化，同时 VFS 对象的所有方法
  基本都重构过，路径查找策略不同。加入了路径缓存。
• Titanix：参考了其一些 C 结构体的设计，以及其动态链接的实现思路。
```
**来源**: Chronix §1.4

**关键**: 不仅要列出参考了谁，还要说明"我们改了什么、为什么不同"。这区分了"继承"和"贡献"。

### 5.3 模块完成情况表

六份文档无一例外地在概述章放了一张"模块→完成情况"的表格，如：

```
模块        完成情况
进程管理    无栈协程调度，支持全局统一的 executor 调度器；实现多线程的资源回收...
文件系统    实现 dentry 构建目录树；实现页缓存和 dentry 缓存...
内存管理    实现基本的内存管理功能；实现 CoW、懒分配内存优化...
```
**来源**: Del0n1x §1.1, Chronix §0(摘要), Noaxiom §1.3

## 六、语言风格铁律

### 6.1 段落结构：声明 → 展开 → 收敛

每个段落遵循三段式：
1. **声明句**（主题句）：直接说出结论或设计选择
2. **展开句**（2-4句）：解释原因、给出细节、列举例证
3. **收敛句**（可选）：总结效果、指出边界

示例（来自 Chronix §2.2.1）：
```
[声明] Chronix 仿照 Linux 内核，进程线程统一用 TaskControlBlock 表示,通过统一的 API
操作任务，达到简洁有效的统一管理。
[展开] Chronix 基于 rcore ch6 进行开发，其原始设计明确区分设计了 Process 和 Thread...
但是 Linux 内核对 task 这一单位结构的实现更具启发性：它并未严格区分进程和线程...
其次 rcore 设计中使用了大锁来保护内部可变性，但是这样的设计往往降低运行效率...
[收敛] 综上所述 Chronix 参考 Linux 采用统一的 TaskControlBlock 表示任务将其作为调度
的基本单元，并在此基础上进行扩展，增加了一些新的字段并将字段分类。
```

### 6.2 代码展示规范

- 每份文档的代码块都有**编号和标题**：`代码片段 X.X  描述`
- 代码块之后**必须有**文字解读，不能代码连代码
- 解读不是复述代码，而是解释**为什么这样写**、**字段为什么这样分类**

### 6.3 图表引用规范

所有图表使用统一格式：`图 X-X  描述` / `表 X-X  描述`
图表不单独存在，必须在正文中有"如图 X-X 所示"的引用。

## 七、深度控制：什么详细写、什么简略写

六份文档的"详细程度"遵循一个清晰的选择逻辑：

### 详尽展开的（有代码+有图+有解读）
- **原创设计**：自研 HAL 层、自研调度器、独特的 VFS 设计
- **架构差异**：RV64 与 LA64 的页表差异、trap 差异、启动差异
- **性能优化**：COW、懒分配、页缓存、路径缓存
- **关键 Bug**：根因→定位→修复→教训的完整链路

### 简略带过的（一句话或一个表项）
- **标准实现**：FAT32 驱动的标准参数、bitflags 定义
- **第三方依赖**：lwext4 原理（引用官方文档即可）、smoltcp 协议栈
- **常规系统调用**：没有特殊设计的 syscall 只出现在 syscall 列表表中

### 判断标准
> 如果这个设计是"照着 Linux man page 或教科书写就能做出来的" → 简略
> 如果这个设计是"我们团队做了独特的工程取舍或架构创新" → 详尽

## 八、从零生成文档骨架的流程

### Phase 1：确定章节目录
1. 根据内核实际模块，选择 11 章标准骨架中的相关章节
2. 为每章写一句话的"本章回答的核心问题"
3. 确认章间无职责重叠

### Phase 2：为每章生成小节骨架
1. 按五段式模板为每章规划 3-6 个小节
2. 每个小节写一句话的"本节目的"
3. 标注哪些小节需要代码块、哪些需要流程图

### Phase 3：建立证据索引
1. 为每个小节登记对应的源码文件路径
2. 标记关键 commit
3. 标记"待验证"和"待人工确认"项

### Phase 4：逐章填充正文
1. 按五段式模板展开每个小节
2. 代码块→逐段解说
3. 设计对比→理由陈述
4. 收敛检查：每章开头有概述、结尾有总结
