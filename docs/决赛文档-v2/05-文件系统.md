# 5. 文件系统

> 本章回答：VFS 如何抽象各种文件系统和特殊文件？ext4 如何接入？缓存如何加速？文件描述符如何管理？

RespOS 的文件系统采用分层抽象的 VFS（Virtual File System）架构，通过 dentry、inode、super_block 三层核心 trait 实现了文件访问与后端存储的解耦。这一设计使得上层的 open/read/write 系统调用能在不感知 ext4、procfs、devfs 差异的情况下完成文件操作。

## 5.1 虚拟文件系统——对象模型

> 【本节目的】逐一解释 VFS 核心对象的结构、生命周期和相互关系。

### 5.1.1 五层抽象：从 fd 到磁盘

RespOS 的文件系统栈从用户态文件描述符到最终磁盘数据共跨越五层抽象。这一设计与 Linux 的 `fd → struct file → struct path { vfsmount, dentry } → struct inode` 模型在结构上对齐，但在 Rust 的所有权语义下采用 `Arc` 引用计数而非手动引用计数管理生命周期。

```
int fd（用户态）
    │  FdTable[fd]
    ▼
FdEntry { file: Arc<dyn FileOp>, flags }     ← per-fd 标志（仅 CLOEXEC 有意义）
    │
    ▼
FileOp trait（open-file description）        ← offset、O_APPEND、O_NONBLOCK
    │  File / Pipe / SpecialFd
    ▼
Path { mnt: Arc<VfsMount>, dentry: Arc<Dentry> }  ← 文件系统实例 + 目录缓存项
    │
    ▼
Dentry（目录项缓存）                          ← abs_path + parent(Arc) + children(Weak)
    │  通过 InodeOp trait 访问 inode
    ▼
InodeOp trait（inode 操作）                   ← read_at / write_at / lookup / create
    │  Ext4Inode / ProcInode / DevInode
    ▼
SuperBlockOp trait（超级块）                  ← root_inode() / sync() / statfs()
```

这一架构的核心洞察在于将两个不同生命周期的概念拆分为独立的 trait。`InodeOp` 管理文件自身的属性和数据——它在文件存续期间保持不变，无论该文件被打开多少次，底层的 inode 始终是同一个。`FileOp` 管理打开实例的状态——offset、O_APPEND 语义、O_NONBLOCK 阻塞策略——这些状态属于"这一次打开"，不同进程打开同一文件拥有相互独立的 offset，而 fork 或 dup 复制的 fd 则共享同一个 FileOp 实例和 offset。

### 5.1.2 InodeOp：文件系统后端的最小接口

```rust
// os/src/fs/vfs/inode.rs
pub trait InodeOp: Any + Send + Sync {
    fn node_type(&self) -> InodeType;                          // Regular/Directory/SymLink/...
    fn stat(&self, path: &str) -> SysResult<KStat>;            // 元信息
    fn read_at(&self, path: &str, off: usize, buf: &mut [u8]) -> SysResult<usize>;
    fn write_at(&self, path: &str, off: usize, buf: &[u8]) -> SysResult<usize>;
    fn truncate(&self, path: &str, size: usize) -> SysResult<usize>;
    fn lookup(&self, parent_path: &str, name: &str) -> SysResult<Arc<dyn InodeOp>>;
    fn create(&self, parent_path: &str, name: &str, ty: InodeType) -> SysResult<Arc<dyn InodeOp>>;
    fn link(&self, old_path: &str, bare_dentry: Arc<Dentry>) -> SysResult;
    fn unlink(&self, valid_dentry: &Arc<Dentry>) -> SysResult;
    // 多个可覆盖的默认方法: get_page_cache / set_times / set_mode / set_owner / xattr...
}
```

InodeOp trait 共 20 个方法，其中 10 个提供默认实现返回 `EINVAL` 或 `ENOSYS`。这种设计允许后端文件系统只实现自己支持的语义而忽略无关操作。例如 procfs 的 `read_at` 是动态生成字符串而非读取磁盘块，其 `set_times` 和 `set_mode` 继承默认的 EINVAL 拒绝；ext4 则几乎全覆盖。这种"按需覆盖"的策略在功能完整性和代码简洁性之间取得了平衡。

### 5.1.3 FileOp：打开文件的统一操作接口

```rust
// os/src/fs/file.rs
pub trait FileOp: Any + Send + Sync {
    fn read<'a>(&'a self, buf: &'a mut [u8]) -> SysResult<usize>;
    fn write<'a>(&'a self, buf: &'a [u8]) -> SysResult<usize>;
    fn read_at_offset(&self, offset: usize, buf: &mut [u8]) -> SysResult<usize>;  // pread
    fn write_at_offset(&self, offset: usize, buf: &[u8]) -> SysResult<usize>;     // pwrite
    fn seek(&self, offset: isize) -> SysResult<usize>;
    fn get_flags(&self) -> OpenFlags;
    fn readable(&self) -> bool;
    fn writable(&self) -> bool;
    fn read_ready(&self) -> bool;        // 非阻塞模式下的数据可用性
    fn write_ready(&self) -> bool;       // 非阻塞模式下的写空间可用性
    fn fsync(&self) -> SysResult<usize>; // 脏页 → inode → 超级块刷盘
    fn truncate(&self, size: usize) -> SysResult<usize>;
    fn register_poll_waiter(&self, tid: usize, events: PollEvents) -> bool;
}
```

FileOp trait 的默认实现体现了清晰的分类策略。普通文件默认 `read_ready()` / `write_ready()` 永远返回 true——数据立即可得，无需阻塞等待。pipe 覆盖这两个方法为"缓冲区非空/非满时返回 true"，并覆盖 `register_poll_waiter` 注册 epoll 通知。pread/pwrite 方法默认返回 `ESPIPE`——仅支持 seek 的 fd 类型才实现。这种"不做不该做的事"的默认策略使得添加新的 fd 类型变得安全。

### 5.1.4 Dentry：路径到 inode 的缓存映射

Dentry 不仅是缓存——它是 VFS 层路径命名空间的核心数据结构。其设计面临 Rust 所有权模型下的一个根本张力：如何在保证内存安全的前提下维护一棵带有双向引用的树结构。

```rust
// os/src/fs/vfs/dentry.rs
pub struct Dentry {
    pub abs_path: String,                       // 文件全路径
    pub inner: Mutex<DentryInner>,
}

struct DentryInner {
    pub inode: Option<Arc<dyn InodeOp>>,        // None = 负目录项（缓存"文件不存在"）
    pub parent: Option<Arc<Dentry>>,            // 父目录（强引用，保证路径追溯可靠）
    pub children: HashMap<String, Weak<Dentry>>,// 子目录（弱引用，打破循环）
    alias_path: Option<String>,                 // rename 后的新路径覆盖
}
```

parent 选择强引用（`Arc`）而 children 选择弱引用（`Weak`）是一个经过权衡的设计决策。完整路径通过沿 parent 链递归拼接分量名获得——如果 parent 是弱引用，每次向上追溯都可能因缓存淘汰而中断，需要从根目录重新走 namei 解析。强引用保证了"只要子 dentry 存活，父 dentry 一定活着"的不变性，路径追溯永不失败。children 用 `Weak` 的代价是 `remove_dentry_cache_tree`（unlink/rename/umount 时清除子树缓存）只能通过 O(n) 全局前缀扫描实现，因为无法沿弱引用链可靠遍历所有子孙。

**全路径存储的设计选择**。RespOS 选择存储完整绝对路径（`abs_path: String`）而非 Linux 的分量名（`d_name`）模型。这一选择的动机是简化路径拼接：`child_abs_path = parent.current_abs_path() + "/" + name`，无需从根目录逐层向上遍历收集分量名。但它引入了两个伴随代价：（1）rename 后旧路径失效，需要 `alias_path` 作为覆盖值；（2）parent 必须用强引用以支持可靠路径追溯，这又迫使 children 用弱引用打破循环。

> 【建议检查的代码】`os/src/fs/vfs/dentry.rs`，`os/src/fs/dentry_cache.rs`

## 5.2 挂载与文件系统实例

> 【本节目的】解释挂载语义和跨文件系统边界的路径穿越。

挂载操作涉及两个正交语义——"被挂载的文件系统是什么"和"这个文件系统挂在树上的哪个位置"。RespOS 通过 `VfsMount` 和 `Mount` 两个独立结构实现这种分离。

```rust
// os/src/fs/mount.rs
pub struct VfsMount {
    pub root: Arc<Dentry>,              // 该文件系统的根 dentry
    pub fs: Arc<dyn SuperBlockOp>,      // 超级块
    flags: AtomicI32,                   // MS_RDONLY / MS_NOATIME / ...
}

pub struct Mount {
    pub mountpoint: Arc<Dentry>,        // 挂载点目录（属于父文件系统）
    pub vfs_mount: Arc<VfsMount>,       // 指向被挂载的文件系统
    pub parent: Option<Weak<Mount>>,    // 父 Mount 节点（弱引用，打破循环）
    pub children: Mutex<Vec<Arc<Mount>>>, // 子 Mount 列表
}
```

路径解析每步的挂载穿越逻辑嵌入在 `lookup_dentry` 中：如果当前 dentry 是挂载点，路径游标的 mnt 和 dentry 同时切换到被挂载文件系统的根。`..` 穿越挂载边界时需要特殊处理——被挂载文件系统的根目录从其自身文件系统看 `..` 就是根本身，但在全局命名空间中应指向父文件系统的挂载点目录。`follow_dotdot` 在 Nameidata 当前 dentry 等于所在文件系统根时，沿 `Mount.parent` 链退回父 Mount 的挂载点。

内核当前仅有一个 ext4 超块实例，所有挂载（包括 procfs、devfs、tmpfs）最终共享同一个磁盘镜像上的 ext4 目录树。块设备挂载通过 `MountBackingRoot` 机制实现隔离——在真实 ext4 根下创建隐藏目录作为每个 mount 的文件系统根。

> 【建议检查的代码】`os/src/fs/mount.rs`，`os/src/fs/namei.rs`

## 5.3 路径解析

> 【本节目的】解释从路径字符串到目标文件的一次完整 namei 过程。

namei（Name Index）是将用户提供的路径字符串逐层解析为 `Path { mnt, dentry }` 的完整引擎。其核心结构 `Nameidata` 是解析过程中的状态游标——记录当前所在的文件系统、目录项和尚未解析的路径分量列表。

`link_path_walk` 是逐分量解析的主循环：对每个路径分量，先查 dentry 缓存（命中时仅需一次 HashMap 查找加一次挂载点检查），缓存缺失时调用 `inode.lookup(name)` 创建新 dentry。遇到符号链接时，剩余分量和链接目标拼接成全新路径，通过 `continue 'restart` 重新开始解析——这种迭代式展开而非递归调用避免了深层符号链接嵌套下的栈溢出风险，同时复用了 symlink 跟随计数（`MAX_SYMLINK_FOLLOWS = 40`）的深度限制。

RespOS 实现了四个 `AT_*` 标志位：`AT_FDCWD`（相对路径从 cwd 开始）、`AT_SYMLINK_NOFOLLOW`（最后一级分量不展开符号链接）、`AT_EMPTY_PATH`（空路径操作 dirfd 自身）、`AT_NO_AUTOMOUNT`（当前仅有白名单支持）。

全局 `NAMEI_MUTATION_LOCK` 将 create、unlink、rename、symlink 等修改路径命名空间的操作完全串行化。这一设计简洁且无死锁风险，但代价是写密集场景下的多核并行度完全丧失——在 BuildStorm 等并发创建/删除文件的负载下，多个 CPU 实际在互斥锁上排队。

## 5.4 ext4 后端与页缓存

> 【本节目的】解释 ext4 文件系统如何接入 VFS，以及页缓存如何加速读写。

### 5.4.1 ext4 后端

RespOS 通过 Rust FFI 绑定 C 库 lwext4 实现 ext4 文件系统的读写。这一架构意味着内核的文件系统层是一个适配层——将 VFS 的 `InodeOp` trait 方法翻译为 lwext4 的 C 函数调用——而非直接操作 ext4 磁盘数据结构的原生实现。

`Ext4Inode` 在 lwext4 基础上维护了额外的内核状态层，覆盖了 lwext4 不直接管理的语义：

- **open_files**：文件打开计数。每次 File 构造时递增，File drop 时递减，用于判断 unlink 时是否需要转为孤儿文件
- **nlink_override**：inode 链接数的内存覆盖值。unlink 后设为 0（告知 stat 该文件已无链接），但被打开的 fd 仍然可以读写
- **orphan_path**：孤儿文件的磁盘路径。unlink 时将文件 rename 为隐藏名 `.respos_orphan_<ino>`，最后一个 fd 关闭时真正删除

这个"孤儿文件 = rename 到隐藏名 + nlink_override 模拟"的机制是对 Linux 孤儿 inode 模型的模拟。Linux 通过 `i_nlink == 0 && i_count > 0` 的双计数器语义自然支持"已 unlink 但仍在使用的 inode"，而 lwext4 的 API 缺乏这一抽象——它只提供 `file_remove`（直接删除目录项和文件），不提供"仅减少 nlink 但保留 inode"的中间状态。RespOS 的 rename-to-hidden 策略在应用层实现了等价语义。

ext4 后端的一个核心特征是 path-based：所有 inode 操作都需要传递完整的文件路径字符串。这是因为底层 lwext4_rust 通过路径而非 inode 号在磁盘上定位文件。这一限制导致硬链接的实现需要额外的 dentry 层协调——同一个 inode 在两条不同路径下被访问时，必须确保 dentry 层正确跟踪了路径别名。

### 5.4.2 页缓存设计

页缓存是文件数据在内存中的缓冲区，其设计核心是在低 I/O 延迟和有限内存之间取得平衡。

```
Page（单页）：
  data: Vec<u8>（PAGE_SIZE 字节）
  dirty: bool                         ← 被写过但未刷盘
  write_version: usize                ← sync 时的并发写检测版本号
  generation: usize                   ← 全局 LRU 代数

PageCache（per-inode）：
  pages: Mutex<BTreeMap<usize, Arc<Mutex<Page>>>>  ← 稀疏存储：只存实际访问过的页
  file_size: Mutex<usize>
  dirty_pages: AtomicUsize            ← 该缓存中脏页总数
```

页缓存的存储方式是**稀疏的**——一个 1 GB 的文件只被访问了前两页时，BTreeMap 中只有两个 Page 对象。这种按需分配策略避免了在文件打开时全量分配缓存页的内存浪费。

四个操作构成了页缓存的完整生命周期：

**read_at**：逐页遍历 → 查 pages BTreeMap（缓存命中则直接 memcpy）→ miss 时构造新 Page → 通过 ext4 读入数据 → 插入 BTreeMap → 推入全局 LRU → 检查全局内存配额。

**write_at**：分两条路径处理——整页覆盖或写超出文件末尾的新页时直接分配零页（不需要磁盘 I/O 补原数据），部分覆盖现有页时先读入旧数据再覆盖写入区域。写入后标记 `page.dirty = true`，但此时数据仍在内存中，未触及磁盘。

**sync**：fsync 或 O_SYNC 写触发的脏页写回。先快照脏页的 `write_version`（用于并发写检测），然后按连续脏页分组批量写回。写回后双重检查：`size_version` 是否变化（并发 truncate/extend 修改了文件长度）；`write_version` 是否与快照一致（并发写重新弄脏了页）——仅清理版本号未变的页的 dirty 标记。

**reclaim_global**：内存压力触发的全局回收。采用 generational LRU 算法——从队首弹出最老条目，比较 generation 与 Page 中记录的当前 generation。不匹配说明页面已被重新访问过，跳过；匹配且 `page.dirty == false` 且无外部引用才真正从 BTreeMap 中删除。脏页永远不会被 LRU 回收——脏数据的释放机制是 `sync` 而非回收。

### 5.4.3 持久化写回的三层链

文件数据的持久化经过三级缓存，每一级都有独立的刷盘触发条件：

```
用户 write()
  → page_cache.write_at()           ← 内存标脏，不碰盘
    （脏页积累直到：O_SYNC/O_DSYNC 触发或 fsync 触发或内存压力）
  → page_cache.sync(inode, path)
      → inode.write_at(path, off, data)  ← 页缓存 → lwext4 内部写缓冲区
        （数据在 ext4 内部，但可能仍被 lwext4 缓冲）
  → superblock.sync()
      → ext4_cache_flush()               ← lwext4 缓冲区 → virtio 块设备
        （数据真正到达磁盘镜像）
```

普通 `write()` 停留在第一级。`O_DSYNC`/`O_SYNC` 写推至第二级。只有显式 `fsync`、File::drop（关闭最后一个 fd 的引用）或 `sync` 系统调用才将三级全部打穿。

> 【建议检查的代码】`os/src/fs/page_cache.rs`

## 5.5 文件描述符管理

> 【本节目的】解释 FdTable、FdEntry 和 open-file description 的三层关系。

文件描述符采用"两层共享"设计。`FdTable` 是 per-process 的 fd 槽位数组，使用线性表加回收队列的结构——`close` 时将 fd 号推入回收队列并排序，`alloc_fd` 时优先取回收队列中未使用的最小 fd，符合 Unix 标准要求。`FdEntry` 包含 CLOEXEC flag 和 `Arc<dyn FileOp>` 的共享引用。

普通 fork 复制 fd table（复制槽位数组），父子可以独立 close、dup 和设置 CLOEXEC，但表内的 `FdEntry` 仍持有相同 `Arc<FileOp>`，从而共享文件偏移和 pipe 端点。`CLONE_FILES` 则直接共享整张表——同组线程操作同一组 fd。exec 时，RespOS 会先解除 `CLONE_FILES` 共享（`unshare_fd_table_for_exec`），再在新表上执行 `close_on_exec()` 清理标记了 CLOEXEC 的 fd，避免 child exec 错误关闭父进程的描述符。

这条 fd 生命周期经历过一次真实的压力修复。早期实现只要发现 `FdTable` 有多个 `Arc` 引用就复制，但多线程 exec 摘除的旧 TCB 会因内核栈延迟回收继续持表，导致 pipe 写端无法降到零。现在 `unshare_fd_table_for_exec()` 先为执行者建立私有表，再通过 `TASK_MANAGER` 区分"仍存活的共享者"和"只剩延迟 TCB 的引用"——没有 live sharer 时主动清理旧表。

>
