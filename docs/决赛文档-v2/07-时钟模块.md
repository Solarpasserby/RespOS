# 7. 时钟模块

> 本章回答：时钟中断如何管理？定时器如何设计？用户态的 sleep/timer 如何实现？

## 7.1 概述

RespOS 将"读取时间"和"等待事件"分开处理。硬件计数器提供基础时间，syscall 层再构造用户可见的 clock。定时器管理采用时间轮和最小堆混合数据结构——时间轮负责粗粒度的周期性检查，最小堆管理精确的超时事件。

## 7.2 时钟源与时钟中断

**RISC-V 时钟**。RISC-V 通过 mtime/mtimecmp 寄存器提供硬件计时，SBI 接口封装了设置下一次时钟中断的操作。`timer.rs` 负责编程 mtimecmp 寄存器以触发下一次时钟中断。

**LoongArch 时钟**。LoongArch 通过 TCfg（配置）和 TIClr（清除）两个 CSR 管理时钟。恒等时钟频率可通过 `cpucfg` 指令直接获取，因此 LA 的时钟频率无需硬编码。时钟初始化的时机有一个特殊约束：获取的时钟频率需存入静态数据区域，必须在 bss 段清零之后才能进行。

**时钟中断处理**。timer trap 进入后先重新编程下一次时钟中断，然后更新系统运行时间。多核版本的 timer 处理还有一个额外的安全约束：全局扫描（检查 futex、sleep、timerfd 是否到期）固定由 timer service hart 负责，并且只在它从用户态进入 timer trap 或处于 idle context 时执行——避免在 syscall 持锁期间突然再次进入同一把锁造成死锁。

> 【建议检查的代码】`os/src/arch/*/timer.rs`

## 7.3 定时器队列

定时器队列采用时间轮和最小堆混合结构。时间轮将时间划分为固定大小的槽位，每个槽位用链表挂接到期时间落在该槽位内的定时器。时间轮的轮转是 O(1) 的——时钟推进时只处理当前槽位。对于超出时间轮范围或需要精确超时的事件，改用最小堆按绝对到期时间排序。

**内核定时器**注册时计算绝对到期时间，插入对应槽位或堆中。时钟中断处理时检查当前槽位中的所有定时器，到期则触发回调（通常是唤醒阻塞任务）。**用户定时器**（nanosleep、interval timer）则在内核定时器的基础上增加了用户态可见语义——nanosleep 的剩余时间计算、interval timer 的周期重装载、timerfd 的可读计数。

> 【建议检查的代码】`os/src/task/` 中定时器相关代码（timer wheel / scheduler timer 检查）

## 7.4 用户态时间接口

RespOS 提供以下用户态时间与定时器接口：

| clock / timer | 当前语义 | 主要用途 |
| --- | --- | --- |
| `CLOCK_REALTIME` | monotonic 加一个可调整 offset | 日历时间、绝对 deadline |
| `CLOCK_MONOTONIC` | 来自持续增长的硬件运行时间 | timeout 和相对计时 |
| coarse clock | 将时间量化到 1 ms | 低开销粗粒度查询 |
| nanosleep | 登记 deadline 后阻塞任务 | 可被 signal 打断并返回剩余时间 |
| interval/POSIX timer | 到期后向进程投递 signal | alarm 和周期通知 |
| timerfd | 到期次数通过 fd 读取 | 与 poll/epoll 统一等待 |

时间记录的精度经历了从毫秒到微秒的优化。早期 sleep 和 futex timeout 以毫秒记录截止时间，部分短等待会提前醒来。现在相关记录调整到微秒，并把 realtime 的可调偏移与 monotonic 分开——修改系统时间不会让内部 timeout 跟着跳变。

timer 的对象生命周期也采用先准备、后提交的原子性保证。`timer_create` 在 id 成功写回用户态后才发布对象；`timer_settime` 在 old value 写回成功后才修改 deadline；进程组退出会按 owner 删除全部 POSIX timer。

timerfd 已支持 realtime、monotonic 和 boottime 三种时钟源。alarm clock 与 `TFD_TIMER_CANCEL_ON_SET` 因语义不完整而明确拒绝。当前仍不支持真正的线程 CPU clock、suspend/TAI 和 wakeup alarm。

> 【建议检查的代码】`os/src/syscall/time.rs`，`os/src/syscall/special_fd.rs`
