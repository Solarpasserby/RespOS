# 3. 中断与异常处理

> 本章回答：用户态和内核态的 trap 如何进入、分发、返回？双架构差异如何统一？

## 3.1 概述

trap 处理是内核的"入口守卫"——负责从用户态进入内核、将异常分发给正确的处理函数、在完成后安全返回用户态。RespOS 将硬件相关的 trap entry/return 逻辑收敛在 HAL 层，公共的 trap 分发逻辑复用同一套 `trap_handler`。

> 【建议写什么】
> - trap 处理的职责范围：用户态陷入、内核态中断、系统调用、缺页异常、时钟中断
> - 架构相关部分收敛在 HAL 层，公共逻辑复用在 `trap_handler` 中
>
> 【建议检查的代码】`os/src/arch/*/trap/`

## 3.2 特权级切换流程

一次完整的用户态陷入到返回经过三个阶段：

**trap entry（汇编）**。硬件自动保存 PC 到 sepc/ERA、原因到 scause/ESTAT，然后跳转到 trap vector。RespOS 的汇编 entry 路径负责保存所有通用寄存器到栈上的 `TrapContext`，然后调用 Rust 的 `trap_handler()`。这一阶段最关键的设计选择是：内核态 trap 不需要单独保存上下文，直接将寄存器快照留在当前内核栈上，视为一次函数调用。

**trap 分发（Rust）**。`trap_handler()` 根据 trap 原因进行分发：系统调用走 `syscall()` 入口；缺页异常走 `page_fault_handler()`；时钟中断走 timer 处理并可能触发调度；外部中断走 PLIC 或 Line-Based Interrupt 处理。如果 trap 来自内核态（如内核自身的缺页），处理逻辑与用户态 trap 不同——内核态异常通常是 bug，需要 panic 而非尝试恢复。

**trap return（汇编）**。从 `TrapContext` 恢复所有寄存器，执行 `sret`（RISC-V）或 `ertn`（LoongArch）返回用户态。RV64 的返回路径有一个关键的顺序要求：必须先清除 SIE 位（禁止中断）、恢复通用寄存器、最后才切换用户态 trap vector——如果提前切换 vector，timer 中断可能在寄存器未完全恢复时重入，导致递归异常。

## 3.3 TrapContext 设计

`TrapContext` 是陷入时寄存器快照的 Rust 表示。两种架构的 TrapContext 在概念上对齐——都包含通用寄存器、PC、trap 原因和用户栈指针——但底层 CSR 映射不同。

```rust
// TrapContext 核心字段（概念结构）
pub struct TrapContext {
    pub x: [usize; 32],     // 通用寄存器 x0-x31
    pub sepc: usize,        // 用户态 PC（RISC-V sepc / LA ERA）
    pub sstatus: usize,     // 用户态状态寄存器（RISC-V sstatus / LA CrMd+Euen）
    pub stval: usize,       // trap 附加信息（RISC-V stval / LA BAdv）
    pub user_sp: usize,     // 用户态栈指针
    pub kernel_sp: usize,   // 内核栈指针，用于恢复时切回内核栈
}
```

RISC-V 和 LoongArch 在寄存器编号上有对应关系（x0-x31 对应 r0-r31），但 CSR 寄存器完全独立。HAL 层的 entry/return 汇编负责架构 CSR ↔ 通用 TrapContext 字段的转换。

> 【建议检查的代码】`os/src/arch/rv64/trap/context.rs`，`os/src/arch/loongarch64/trap/context.rs`
>

## 3.4 中断控制器

**RISC-V 中断模型**。RISC-V 使用 PLIC 管理外部中断。PLIC 接收来自多个设备的中断请求，根据优先级和使能配置发送给特定的 hart。内核通过 MMIO 地址访问 PLIC 寄存器完成中断使能、优先级设置和中断认领（claim）/完成（complete）。

**LoongArch 中断模型**。LoongArch 使用 Line-Based Interrupt 模型，中断使能需要经过多级配置：ECfg（设置中断向量类型）→ TCfg（时钟中断源使能）→ CrMd（当前模式的中断总使能位）。这种多级使能设计意味着一个外设中断要真正触发，需要同时满足多个条件，调试时容易遗漏某一级。

> 【建议检查的代码】`os/src/arch/*/trap/mod.rs`

## 3.5 双架构 trap 差异与关键安全约束

两种架构的 trap 处理存在几个影响安全的关键差异：

**SIE 清理顺序（RV64）**。这是从实际 bug 中提取的教训。早期 `__restore` 在寄存器恢复前就切到用户态 trap vector——timer 中断在寄存器处于中间状态时到达，导致第二次 trap。修复后的顺序固定为：清 SIE（禁止中断）→ 恢复寄存器 → 最后切换 user vector。这一约束同样适用于 signal handler 和 sigreturn 路径。

**LoongArch 的多级中断使能**。LA 的中断需要 ECfg（中断向量类型）→ 中断源使能（如 TCfg 的 timer 位）→ CrMd（当前模式总使能）三层同时打开。遗漏任何一级都会导致中断静默失效。

**LoongArch 的 ertn 行为**。与 RISC-V 的 `sret` 类似，`ertn` 将 ERA 恢复到 PC 并切换特权级。但 LA 的 `ertn` 还会从 CSR 恢复其他 CPU 状态（如 CrMd），这意味着 trap return 前必须确保这些 CSR 处于期望的值。
